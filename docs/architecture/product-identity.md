# 产品标识与命名迁移（Product Identity）

- 状态：**规范冻结（文档）**；本文件只定义规则，**不执行任何改名**
- 范围：产品名称、中文品牌名、旧名称的定位、命名规则与迁移策略
- 与 ADR-001 的关系：本文件是 ADR-001 的补充，**不修改、不替代** ADR-001；ADR-001 中的“NiuMa”指评估对象，仍按其原意阅读

## 1. 官方名称

| 项 | 名称 | 定位 |
| --- | --- | --- |
| 英文产品名 | **Virtual AI Office** | 当前产品与未来架构的正式名称 |
| 中文品牌名 | **智序工场** | 当前产品的正式中文品牌名 |
| 旧名称 | **NiuMa / 牛马工作室** | **Legacy NiuMa Runtime**：旧运行时与兼容层，不再是产品名 |

关系（冻结）：

```text
Virtual AI Office / 智序工场   →  当前产品与未来架构
NiuMa / 牛马工作室             →  Legacy NiuMa Runtime（旧运行时 / 兼容层）
```

**“虚拟智能办公室”不再是官方中文名。** 新文档、新界面、新代码注释中不得再使用它作为产品名。

## 2. 中文品牌定义

“智序工场”是**中文品牌名，不是 “Virtual AI Office” 的直译**，两者不要求逐字对应。

| 字 | 意图（大意，非法律翻译） |
| --- | --- |
| 智序 | 由智能驱动的、有秩序的协同 |
| 工场 | 人类员工与 AI Agent 共同工作、协作与产出的生产环境 |

这一解释用于说明品牌意图，**不作为法律或商标意义上的翻译**。中英文品牌各自独立使用，不互相“回译”。

## 3. 术语表

| 术语 | 含义 | 规则 |
| --- | --- | --- |
| **Virtual AI Office** | 产品英文名；也指由人类成员与 AI Agent 成员共同组成的办公室 | 面向用户的英文场合使用 |
| **智序工场** | 产品中文品牌名 | 面向用户的中文场合使用 |
| **Legacy NiuMa** | 旧运行时（`src/`、`public/`、`bin/`、`fake/`、`desktop/` 中尚未被替换的部分）与旧配置格式 | 只在讨论兼容、迁移时出现；代码与文档中以 “Legacy NiuMa Runtime” 指代 |
| **牛马工作室** | 旧产品的中文名 | 只用于指代旧产品，**不得**用于新功能、新界面、新文档 |
| **Workspace** | 一间办公室：成员、角色目录、执行器配置、配额的归属者 | 领域实体，见 `domain-model.md` |
| **Project** | Workspace 内的一个项目 | 领域实体 |
| **Member** | 办公室中的一员，`kind: human \| agent` | 单一抽象，**不**拆成 Human / Agent 两种实体 |
| **Human Member** | `kind = human` 的 Member | 唯一能做最终审批的成员类型 |
| **Agent Member** | `kind = agent` 的 Member | 不能持有含 `approve` 权限的角色 |
| **Role** | 一项职责（权限 + 说明），不是模型 | 见 `domain-model.md` |
| **RoleBinding** | Member × Project × Role | 决定某人在某项目中的职责；同一个人在不同项目可以有不同角色 |
| **Executor** | 执行任务的后端（CLI、API 模型、人在回路的 IDE 会话） | 通过 `ExecutorAdapter` 接入；与 Role 解耦 |

| **MemberChannel** | 某位 Human Member 在某个渠道上的已验证身份（通道中立；Telegram 不是 Role，也不是 Member 类型） | 见 `human-channels.md` |
| **HumanActionRequest** | 一条持久记录：Virtual AI Office 正在等待某个具体的人类职责 / 动作（方向是“系统 → 人”，不是“人发起的请求”） | 见 `human-channels.md` |
| **Orchestrator / Office Coordinator** | 新架构中负责编排的中性概念 | 新架构使用中性名称；**不是** “傻妞”，也不得出现 `shaniu` 标识符 |
| **傻妞** | Legacy NiuMa 的总管人设 | 见 §6.1：可作为 Legacy / 可选人设保留，不是新产品编排系统的默认名称 |

## 4. 命名规则

1. **新的面向用户的表面一律使用 “Virtual AI Office” 与 “智序工场”**。
2. **新的代码、实体、API、事件、文档不得引入新的 “NiuMa / 牛马工作室” 命名**，除非该组件**明确**属于旧版兼容层（见 §8）。
3. 旧标识符**不得复用于新架构的概念**。例如不得把新核心的某个模块叫 `niuma-core`，也不得把新事件命名为 `niuma.*`。
4. 品牌名与技术标识符分开管理：品牌名可以改，技术标识符的改名要走 §9 的迁移原则。
5. 新技术标识符使用中性、描述性的名字，不使用中文品牌名的拼音：包作用域沿用 Stage 0 已建立的 `@vao/*`，配置目录、环境变量前缀等新增项使用 `VAO_`（见 §6、§12）。
6. 面向用户的文案中，两个名称的使用场合：中文界面和中文文案用 “智序工场”；英文界面和英文文案用 “Virtual AI Office”；双语并列时写作 “Virtual AI Office / 智序工场”。

## 6. KEEP_TEMPORARILY（暂时保留：LEGACY_COMPATIBILITY_IDENTIFIER）

下列标识符改名会破坏兼容性，**暂时保留**，统一归类为 **`LEGACY_COMPATIBILITY_IDENTIFIER`**。

| 标识符 | 位置（现状） | 为什么暂时保留 |
| --- | --- | --- |
| npm 包名 `niuma-studio` | 根 `package.json` | 发布、安装脚本、桌面打包的引用 |
| `niuma` 命令行 | `bin/niuma.js`、`package.json#bin` | 用户脚本与习惯；桌面壳内部调用 |
| 用户目录 `~/.niuma/`（`config.json`、`logs`、`skins`、`stats.json`）及 `.niuma-studio` | `src/` | 现有用户的配置、日志、皮肤、统计 |
| `NIUMA_*` 环境变量（如 `NIUMA_FAKE`、`NIUMA_FAKE_SPEED`、`NIUMA_DESKTOP_PLATFORM`、`NIUMA_SCREEN_MAX_WIDTH`） | `src/`、`fake/`、`test/` | 现有用户与测试夹具 |
| 旧配置格式与文件名 `niuma.config.json`、`niuma.config.example.json` | `src/config.js`、`desktop/package.json` | 现有用户配置 |
| 内置插件服务器名 `niuma_browser`、`niuma_desktop`（含 `mcp__niuma_browser__*` 工具名） | `src/tools.js`、`src/mcp/` | 已装用户的 Claude Code / Codex 允许列表引用了这些名字 |
| 旧源码路径 `src/`、`public/`、`bin/`、`fake/` | 仓库 | Stage 1 采用绞杀式迁移，旧路径随旧运行时退役 |
| 桌面打包标识：`niuma-studio-desktop`、`appId: io.github.leeeger1.niuma-studio`、`artifactName`、`desktopName`、更新通道仓库名 | `desktop/package.json` | 自动更新、安装目录、系统注册；`appId` 变更等于“另一个应用” |
| 旧日志、旧统计、旧存档文件 | 用户磁盘 | 用户数据 |
| 迁移兼容代码（读取旧配置、旧目录的代码） | 将来的新核心 | 迁移必须能读旧格式 |
| 旧界面中的名称与人设：`牛马工作室`、总管 `傻妞`、五套皮肤 | `public/`、`src/prompts.js` | 旧运行时的一部分，处理方式见 §6.1 |

>
> 指向旧上游仓库地址（`Leeeger1/niuma-studio`）的 `homepage` / `repository` / 更新通道等**仓库元数据**不属于本表：它们不是兼容标识符，而是应当随仓库迁移更新的元数据；其中桌面更新通道会影响已安装用户，切换时机见 §13 的 P2。

### 6.1 Legacy 人设与主题政策（冻结）

**“傻妞”**

- **不是** Virtual AI Office / 智序工场编排系统的默认名称。
- 可以作为 **Legacy NiuMa 人设 / 可选人设**保留（继续在 Legacy NiuMa Runtime 中使用）。
- 新架构使用中性概念：**Orchestrator / Office Coordinator**；新的代码、实体、事件、API、Telegram 文案**不得**创建名为 `shaniu` 的标识符，也不以“傻妞”作为系统的默认称呼。

**现有视觉皮肤 / 主题（樱花、夜班、赛博霓虹、猫耳咖啡、像素复古，以及 `docs/skins/` 中的皮肤文件格式）**

- **保留，不删除。**
- 归类为 **Legacy 可复用视觉资产**。
- Stage 1C 可以把它们作为**可选主题**提供给新壳；
- 它们**不定义**新产品的品牌；新产品的品牌视觉另行确定。

## 7. RETIRE_LATER（以后退役）

下列标识符在新核心达到功能对等后**必须消失**（可以经过一段兼容期）。

| 项 | 退役方式 |
| --- | --- |
| `niuma` 命令行 | 先提供新命令名；旧命令保留为转发别名并提示；兼容期结束后移除 |
| `niuma-studio` 包名与桌面 `appId` / 更新通道 | 新壳以新标识发布；提供旧版到新版的迁移与更新引导；旧通道关闭 |
| `~/.niuma/` 与 `NIUMA_*` | 新核心使用 `VAO_*` 与新目录；提供一次性迁移，旧目录只读保留一段时间，不自动删除 |
| `niuma.config.json` 格式 | 导入器把旧配置转换为 Workspace / ExecutorConfig / Role；之后旧格式只读 |
| `niuma_browser`、`niuma_desktop` 插件名 | 新插件名上线后保留旧名别名，直到用户配置迁移完成 |
| `src/coordinator.js`、`src/server.js`、`public/app.js` 及其他 Legacy NiuMa Runtime 代码 | ADR-001 的 “对等后切换” 步骤：桌面壳切到新核心后退役 |
| 旧界面中的 “牛马工作室” 文案 | 随旧界面退役，或在对等前的改名任务中替换 |
| 兼容层与迁移代码本身 | 兼容期结束后删除 |

## 8. 禁止的新用法

以下用法**一律禁止**（评审中可直接拒绝）：

1. 在新功能的界面、文案、截图、官网、通知中使用 “牛马工作室” 或 “NiuMa” 作为产品名。
2. 在新核心的包、模块、类、类型、表、事件、API 路径、配置键中新增 “niuma” 字样（包括拼音缩写）。
3. 把 `LEGACY_COMPATIBILITY_IDENTIFIER` 复用于新概念（例如用 `~/.niuma/` 存放新核心的数据，或用 `NIUMA_*` 控制新核心的行为）。
4. 把 “虚拟智能办公室” 当作中文产品名。
5. 在新文档中把旧运行时描述成“当前产品”。
6. 用 “智序工场” 的拼音或缩写作为技术标识符。
7. 在没有迁移与回退方案的情况下，批量替换 §6 中的任何标识符。

允许出现 “NiuMa” 的情形：明确属于旧版兼容层的组件（路径、注释、测试、迁移代码）、对旧行为的描述（写作 “Legacy NiuMa”）、ADR-001 的历史引用、第三方上游仓库的引用与许可证署名。

## 9. 迁移原则

1. **先新后旧**：新东西直接用新名字；旧标识符在兼容期内保持可用。
2. **不盲目改名**：任何会改变用户数据位置、命令、环境变量、安装标识、更新通道的改名，都必须先有迁移与回退方案。
3. **数据不丢**：用户配置、日志、皮肤、统计、存档必须能迁移到新位置；迁移是复制而非移动，旧数据保留到用户确认。
4. **可回退**：每一类标识符的改名是独立的、可单独回退的变更。
5. **别名先于移除**：先让新名字可用，再让旧名字成为别名并提示，最后才移除。
6. **一次只动一类**：品牌文案、命令行、配置目录、环境变量、桌面打包标识分开推进，避免一次变更同时影响多个用户可见面。
7. **兼容层有边界**：兼容层只做读取旧格式与转发，不承载新功能。

## 10. 退役条件

`LEGACY_COMPATIBILITY_IDENTIFIER` 只有在下列条件**全部**满足后才能退役：

1. **新桌面壳成为默认**：新核心驱动的桌面壳已发布为默认下载，并达到旧运行时的功能对等（ADR-001 的“对等后切换”）。
2. **配置迁移存在并经过验证**：旧配置、旧 `~/.niuma/` 数据能自动导入，导入有测试覆盖，且迁移后回退可行。
3. **旧运行时不再被需要**：没有任何用户可见功能仍依赖 Legacy NiuMa Runtime。
4. **旧命令兼容期结束**：`niuma` 别名已提示弃用，并经过公告规定的期限（期限在发布计划中确定，不在本文件中拍脑袋写死）。
5. **现有用户可以无损迁移**：用户配置、历史记录、皮肤、统计均已迁移或可导出；更新通道已指向新应用。
   - **桌面标识专项**：只有在存在经过验证的迁移策略（已安装用户能够从旧 `appId` / 更新通道平滑升级到新标识，且回退可行）之后，才允许切换旧桌面应用的标识与更新通道；在此之前它们保持不变。
6. **文档与支持材料已更新**：新名称覆盖所有对外文档、官网与引导。

只满足部分条件时，对应标识符继续保留。

## 12. 新增技术标识符的约定

- 包作用域：`@vao/*`（Stage 0 已建立）。
- 环境变量前缀：`VAO_`。
- 事件命名空间、实体、表名使用描述性的领域词汇（`member`、`task`、`approval`…），不含品牌词。
- 新数据目录与新配置文件名在 Stage 2A 的持久化设计中确定，**必须**避开 §6 所列旧路径与文件名。
