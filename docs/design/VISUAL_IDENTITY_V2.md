## 2. 定位

**Neo Operations Studio / Digital AI Office**——一间由人类成员与 AI Agent 成员共同运转的数字化办公室。

| 维度 | 方向 |
| --- | --- |
| 气质 | 专业，但不是“企业软件式的沉闷”；清爽、有秩序、有一点温度 |
| 空间 | 现代 2.5D 空间办公室（等距视角），模块化布局 |
| 界面 | 干净的模块化面板；信息密度适中；状态一眼可读 |
| 角色 | 成年、专业、友好的简化 2.5D / Q 版比例角色（见 `CHARACTER_SYSTEM_V1.md`） |
| 语气 | 清晰、克制、可信；不卖萌、不玩梗 |

### 2.1 视觉要传达的十一件事

每一条都必须在产品里有**具体的视觉载体**，而不是口号：

| 要传达的 | 视觉载体 |
| --- | --- |
| 编排（orchestration） | Helix 位于画布中心，向各角色座位发出连线；连线显示任务流向 |
| 秩序（order） | 等距网格、对齐的模块、统一的间距与圆角；区域（Zone）有明确边界 |
| 协作（collaboration） | 角色座位之间的评审线、交接线；人类与 AI 座位同处一个空间 |
| 执行（execution） | 座位上的任务卡、进度脉冲、尝试次数标签（#1 / #2 重试） |
| 透明（transparency） | 每个视觉变化都来自一条真实事件；可展开的事件日志；状态不靠“装饰动画” |
| 人类 + AI 团队合作 | 圆形 HUMAN 徽章与六边形 AI 徽章并列；Human Action 标记 |
| 项目结构 | 组织轨（Workspace → Project → Roles → Members）；画布按项目切换 |
| 任务状态 | 状态环 + 字形 + 动效（三重编码，不只靠颜色） |
| 证据（evidence） | 证据芯片：build / test / review / human，带通过 / 失败 / 缺失标记与提交短哈希 |
| 审批（approvals） | 琥珀色 Human Action 标记，写明负责的角色与成员，“等待回复” |
| 角色职责 | **角色是主要可见身份**；模型只是次要元数据 |

### 2.2 要避免的

- 动漫女友式人设；Legacy 人设“傻妞”及其性格的任何复刻（“傻妞”仅在 Legacy 兼容说明中提及，不定义新身份）；
- “牛马”隐喻与任何牲畜玩笑；
- 过度的 kawaii（卖萌）风格；过量的粉色；
- 把猫耳作为默认身份元素；
- **把模型当作角色身份**（Claude / Codex / DeepSeek 不是角色，也不得设计成永久角色）；
- 旧式卡通反应（汗滴、爱心、冒烟）作为主要状态语言。

## 3. 架构级视觉规则：ROLE ≠ MODEL

这是整个视觉系统的约束，优先于任何审美决定：

1. **角色（Role）是角色形象。** 例如 Helix、Product、Architect、Frontend、Backend、QA、Reviewer、Docs。
2. **模型（Claude、Codex、DeepSeek、GLM、Gemini…）只是徽章 / 运行时分配**：小号中性药丸标签，不是形象、不是颜色主题、不使用厂商品牌色。
3. 同一角色换模型 → 角色形象、座位、配色**完全不变**，只有模型徽章文字变化。
4. **正确与错误的呈现**：

```text
正确：   Architect          错误：   “Claude 角色” / 一个永久带 Claude 品牌的人物
         ◇ AI                        “Codex 小人”
         Claude Sonnet               随模型变色 / 变形象的角色
```

   即：**角色（Architect）→ 成员类型徽章（◇ AI）→ 运行时模型（Claude Sonnet）**，三层信息各自独立。
5. 画布、README、动图里**不得**出现“某个模型 = 某个人物”的呈现。**Helix 位于模型分配之上**：任何模型徽章都不得定义 Helix。

## 4. 成员（Member）的视觉模型

人类与 Agent 都是 Member，视觉上有区分，但**角色仍是主要身份**：

| | Human Member | AI Agent Member |
| --- | --- | --- |
| 徽章形状 | **圆形** HUMAN 徽章 | **六边形**（平顶）AI 徽章 |
| 徽章内字形 | 人形轮廓 | 芯片 / 星芒（节点）轮廓 |
| 附加信息 | 成员显示名；（如存在）通道标记；头像可选 | **模型徽章**（药丸，中性色，如 `Claude`、`Codex`） |
| 位置 | 座位铭牌右下角 | 座位铭牌右下角 |
| 尺寸 | 16 / 20 / 24 px 三档（见 `CHARACTER_SYSTEM_V1.md`） | 同左 |

颜色：徽章用中性描边 + 主题表面色填充，**不使用状态色**（状态色只属于状态环与状态标记）。

### 5.2 字体

不捆绑字体、不引入授权风险，使用系统字体栈：

| 用途 | 字体栈（按顺序回退） |
| --- | --- |
| 界面正文（中文优先） | `"PingFang SC", "Microsoft YaHei UI", "Noto Sans SC", system-ui, sans-serif` |
| 拉丁文与数字 | `Inter, system-ui, "Segoe UI", sans-serif`（Inter 只在本机已安装时使用，不捆绑） |
| 等宽（任务 ID、提交哈希、命令） | `ui-monospace, "Cascadia Mono", "SF Mono", Menlo, Consolas, monospace` |

字阶（px / 行高）：12/16（标注）、13/20（辅助）、14/22（正文）、16/24（小标题）、20/28（标题）、28/36（页面标题）、40/48（展示，仅 README 与大屏）。粗细只用 400 / 500 / 600。数字使用等宽数字（`tabular-nums`）。

### 5.3 面板、形状与层次

- 栅格：**4 px 基础栅格**；间距阶梯 4 / 8 / 12 / 16 / 24 / 32。
- 圆角：面板 12 px、控件 8 px、芯片 999 px（药丸）。
- 层次：深色主题用**描边 + 表面亮度**表达层次（不依赖大阴影）；浅色用 1 px 描边 + 轻阴影（`0 1px 2px rgba(20,32,51,.08)`）。
- 面板标题 14/22 / 600，右上角为面板操作（折叠、更多）。
- 图标：24 px 栅格，1.5 px 描边，圆角端点，单色（继承文字色）；状态字形统一用 16 px。

### 5.4 办公室画布（Office Canvas）

主要的差异化界面，**不是装饰动画**。

- **投影**：等距 2.5D，地砖 64×32（逻辑像素），可缩放 50%–200%。
- **区域（Zone）**：Planning（规划）、Build（构建）、Verify（验证）、Docs（文档）、Human（人类行动区）；每个区域是一块带标签的地面，用 `--canvas-grid` 分隔，不用彩色大块填充。
- **座位（Seat）**：角色形象 + 工位 + 铭牌（角色名、成员徽章、模型徽章）+ 状态环 + 当前任务卡。
- **Helix**：画布中心的特殊座位，向各座位连线（细线，`--accent` 40% 透明度），线上有流动的小点表示正在下发 / 回传。
- **任务卡**：贴附在座位的工位上；显示 `TASK-ID`、标题（单行省略）、状态丝带、依赖数、证据数。
- **依赖边**：从上游任务卡连到下游任务卡。线型：已满足 = 实线；等待 = 虚线；上游失败 = 红色节点（BLOCKED，带 ✕ 字形）。
- **评审线**：Reviewer 座位到被评审任务的细线，线上带结论芯片（通过 / 需修改 / 缺少结论）。
- **证据托盘**：任务卡旁的一排芯片（build / test / review / human），状态为通过 ✓ / 失败 ✕ / 缺失 –，并显示所对应的提交短哈希；与 Stage 0 “证据必须对应当前修订”一致，过期证据显示为灰色 + “过期”。
- **Human Action 标记**：琥珀色标记，写明“需要的角色 + 成员 + 等待回复 + 已等待时长”。
- 图层开关：依赖、评审、证据、Human Action 可以分别开关；默认全部开启。

### 5.5 交互语言

| 项 | 规则 |
| --- | --- |
| 选中 | 2 px `--accent` 描边 + 面板高亮；选中座位 / 任务卡 / 成员互相联动（选中一个，其余相关的高亮） |
| 悬停 | 提亮 6%，显示工具提示（含状态文字）；触屏不依赖悬停 |
| 焦点 | 2 px `--accent` 焦点环，偏移 2 px；键盘可达所有可交互元素 |
| 点击目标 | 桌面 ≥ 32 px；触屏模式 ≥ 44 px |
| 反馈 | 状态变化 120–320 ms 的过渡；破坏性或高风险动作需要二次确认 |
| 动效 | 只表达**真实状态变化**；尊重 `prefers-reduced-motion`（见原型契约） |
| 键盘 | `J/K` 在任务间移动，`Enter` 打开详情，`Esc` 关闭，`/` 聚焦 Helix 输入框，`G` `O` 切换到办公室页（完整清单见原型契约） |

动效令牌：`--dur-fast 120ms`、`--dur-base 200ms`、`--dur-slow 320ms`；缓动 `cubic-bezier(.2,.8,.2,1)`；循环类动效（呼吸、脉冲）周期 1.6–2.4 s，且总是有静态等价形态。

### 5.6 可访问性底线

- 正文对比度 ≥ 4.5:1；非文字元素（状态环、图标、焦点环）≥ 3:1（已在 §5.1 核对）；
- **状态不依赖颜色**：字形 + 线型 + 动效冗余；
- 全部状态都有文字等价（工具提示与屏幕阅读器标签；默认中文，可附英文副标；多语言策略 TBD，见 V7）；
- `prefers-reduced-motion` 下，循环动效替换为静态标记；
- 键盘与屏幕阅读器可完成核心流程（见原型契约的验收标准）。

2. 经典主题的 id、皮肤文件格式（`public/skin-format.js`）、本地皮肤存储、`docs/skins/*.json` **不变、不删除**（`LEGACY_COMPATIBILITY_IDENTIFIER`）。
3. 经典主题**不定义**品牌：README 首屏、官网、产品介绍、新界面的默认外观都使用 Core。
4. 经典主题下的文案仍使用新品牌名“智序工场 / Virtual AI Office”与编排身份 **Helix**（文字品牌迁移已完成，与视觉主题无关）；“傻妞”只允许作为 Legacy 可选人设 / 内部兼容 id，不得出现在默认界面。
5. Core 提供新的**角色形象**（`CHARACTER_SYSTEM_V1.md`）；经典主题继续使用其原有的角色绘制，二者**不混用**（不得出现“Core 画布里夹杂动漫角色”）。
6. 画布渲染接口保持一致（`anime.js` / `office.js` 现有的同一接口）：Core 是**新增**的渲染主题，经典主题的渲染器保持原样，实现细节属于后续实现阶段。

## 8. 新品牌资产的命名与原创要求

- **所有新资产**放在 `docs/brand/`（README 用）与后续约定的应用资源目录下；**文件名不得包含** `niuma`、`牛马`、`shaniu`、`傻妞`（大小写不敏感）。
- 命名：小写、短横线分隔、语义化（`hero-office.png`）；深浅两套用 `-light` 后缀；倍率图用 `@2x`。
- **原创性**：新资产（角色、场景、图标、字标）必须**原创或具备明确授权**；**不得复用 Legacy 的角色、场景图、截图或动图**，也不得模仿任何第三方 IP 的形象；记录每个资产的来源与授权。
- **真实性**：描绘产品界面的图片必须是**已实现界面的真实截图**；在界面实现之前，概念图必须在 alt 文本与说明里标注为“概念图（concept）”。不得用虚构的活动冒充真实产品状态（与“办公室状态来自真实数据，不制造装饰性假活动”的原则一致）。
- Legacy 资产（`docs/demo-anime.gif` 等）保持原文件名与原位置，**不删除、不改名**（改名会破坏已有链接，属于单独的任务）。
