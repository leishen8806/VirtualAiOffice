# 角色系统 V1（Character System V1）

- 产品：**Virtual AI Office / 智序工场**
- 状态：**设计规范冻结稿（仅文档）**；不产出任何图片，不修改任何代码
- 上游：`VISUAL_IDENTITY_V2.md`（调色板、徽章、避免项、ROLE ≠ MODEL）
- 数据语义来源：`docs/architecture/state-machines.md`、`human-channels.md`（Task / Execution / `HumanActionRequest` 状态）

## 1. 核心规则

1. **角色形象代表 Role（职责），不代表 Model（模型）。** 同一角色换模型，形象不变，只换模型徽章。
2. **不得把 Claude / Codex / DeepSeek / GLM / Gemini 设计成永久角色。**
3. **人类与 Agent 都是 Member。** 一个“座位”= 角色形象 + 成员徽章（人类圆形 / Agent 六边形）+（仅 Agent）中性模型徽章。
4. **状态来自真实数据。** 角色的任何状态变化都对应一条真实的 Member / Task / Execution / Event 状态；不制造装饰性的假活动。
5. **Helix 位于模型分配之上。** Helix 是产品内的编排身份，不由任何模型定义；模型（以及规划所用的运行时模型）只出现在详情面板的“运行时分配”里，**不出现在 Helix 的铭牌上**。
6. **正确显示**：`Architect` → `◇ AI` → `Claude Sonnet`（角色 → 成员类型 → 运行时模型）；**错误**：“Claude 角色”或任何永久带厂商品牌的人物。
7. 角色须**成年、专业、友好**，使用简化的 2.5D / Q 版比例，**避免强烈的性别刻板印象**，整套共享一个设计系统。

## 2. 共享设计系统

### 2.1 比例与轮廓

- **比例**：3 头身的简化 Q 版（头 : 身 ≈ 1 : 2）；成年人的体态（肩宽略大于头宽，不用儿童式大头小身）。
- **基础体型**：**一个中性基础体型**（“Operator Base”），通过发型、服装层与配饰区分角色，而不是通过性别化的体型区分；
- **轮廓测试**：把角色填成纯色剪影，在 **48 px 高**下，8 个角色必须能互相区分（靠头部形状 + 一个标志性配饰 + 工位剪影）。
- **等距摆放**：角色面向 3/4 视角（朝右下），工位在右前方；逻辑精灵画布 **96×96**（@1x），地砖 64×32。

### 2.2 线条、着色与面部

- 无黑色外轮廓；用**深一档的同色边缘**（2 px）勾边；
- 着色：**两级阴影**（高光 / 本色 / 阴影），不使用渐变网点；
- 面部：点状眼睛 + 简单眉线 + 小嘴，表情只有 5 种：**neutral（中性）、focus（专注）、curious（好奇）、pleased（满意）、concern（担忧）**；**没有**汗滴、爱心、冒烟、星星眼等卡通反应；
- 肤色与发色：提供 6 档肤色、6 档发色的**通用调色板**（成员可选，见 §5）；不影响角色轮廓与配饰。

### 2.3 服装语言

- 共同的“办公室制服层”：**轻量外套 / 马甲 + 简洁长裤或中长裙 + 平底鞋**（款式中性，不分性别版本）；
- 外套主体用**中性深蓝灰**（深色主题）/ **中性浅灰蓝**（浅色主题）；
- 角色强调色（`VISUAL_IDENTITY_V2.md` §5.1）只出现在**领口镶边、袖口、配饰**上，面积不超过角色可见面积的 15%。

### 2.4 通用元素

| 元素 | 规范 |
| --- | --- |
| 座位铭牌 | 圆角矩形：角色名（中文，13/20）+ 英文角色名（12/16，次要色）；左侧 4 px 角色色条 |
| 成员徽章 | 铭牌右下：人类 = 圆形 HUMAN 徽章；Agent = 六边形 AI 徽章（尺寸 16 / 20 / 24 px） |
| 模型徽章 | 仅 Agent：中性药丸（`Claude` / `Codex` / `DeepSeek` …），文字 11/16，**不使用厂商品牌色、不使用厂商 logo** |
| 状态环 | 角色脚下的椭圆环（等距透视）+ 铭牌上的状态字形（16 px） |
| 任务卡 | 贴在工位屏幕旁：`TASK-ID`、标题、状态丝带 |

## 3. 首批官方角色阵容（8 个）

每个角色都规定：轮廓、服装、配饰、角色图标、强调处理、桌面 / 工位处理。

### 3.1 Helix — System Orchestrator / 系统编排中枢

> **可见名称永远是 Helix**；角色描述（System Orchestrator / 系统编排中枢）只用作副标题。Helix 是官方阵容的**第一个角色**。旧的内部兼容标识符 `shaniu`（Legacy）可以暂时留在代码里，**仅限于明确的兼容说明**，**绝不得**作为默认可见身份，也不得定义本视觉身份。

**Helix 是什么**：产品内的中心编排身份——代表**系统编排、规划、路由、协调、决策可见性、人类交接与执行监督**。

**Helix 不是**：卖萌的 AI 女友；只用来装饰的吉祥物；某个模型厂商的头像；一位人类经理；也不是“傻妞”换了名字、保留同一套性格的替身。其语气为**中性、简洁、陈述事实**（状态消息只说发生了什么与下一步是什么）。

| 项 | 规范 |
| --- | --- |
| 可见铭牌 | 字标 `HELIX`（小型大写字标，等宽字距）+ `Helix`（主）+ `System Orchestrator`（副，中文界面：`系统编排中枢`）+ 状态文字，例如：`HELIX · Planning`、`HELIX · Waiting Human` |
| 成员徽章 | **SYSTEM 节点徽章**（六边形外框 + 内部三节点，双线描边；区别于 Agent 的 AI 徽章与人类的圆形徽章）；**没有模型药丸** |
| 轮廓 | 中性成年 2.5D 体型（Operator Base）；比其它角色略高（+8%）；站姿为主，位于画布中心；头戴**单侧指挥耳麦**形成斜向剪影线，耳麦末端有一个**螺旋（helix）形小挂饰** |
| 配色 | **石墨 / 银灰**为基础（外套石墨、内搭银灰）；**靛紫编排强调色**（`--orchestrator`）只用于镶边与连线 |
| 母题 | 细微的**螺旋 / 节点网络**纹样（外套下摆与桌面的细线）；不使用动物、不使用拟人面孔装饰 |
| 性别编码 | **无强烈性别编码**：中性发型、同一套服装结构、无裙装 / 围裙 / 女仆元素 |
| 服装 | 修身长外套（及大腿），立领；石墨色；不使用任何“制服萌点”元素 |
| 配饰 | 耳麦与螺旋挂饰；胸前**节点徽章**；手持一块半透明**编排面板**（悬浮） |
| 角色图标 | 三个相连的节点（◦—◦—◦ 的等距版本），螺旋线为辅助纹样 |
| 层级 | Helix 的底座是一块**略微抬高的编排平台**（比其它座位高 8–12 px 等距高度），表达“位于模型分配之上” |

**Helix 的工位（指挥台）必须在视觉上连接六类对象**，每类对象一个端口（带图标与计数），从中心底座放射连出：

| 端口 | 连接对象 |
| --- | --- |
| Requirements | 需求 |
| Tasks | 任务 |
| Executions | 执行（尝试） |
| Reviews | 评审 |
| Evidence | 证据 |
| Human Actions | 人类行动（`HumanActionRequest` 等） |

端口的计数与高亮都来自真实数据；没有对象时端口为灰色空心。

**Helix 的可见状态文案**（面板标题区、状态消息、铭牌使用；与 8 个座位状态一一对应，不新增状态）：

| Helix 状态（显示文字） | 中文 | 对应座位状态 |
| --- | --- | --- |
| Planning | 规划中 | THINKING |
| Dispatching | 派发中 | WORKING |
| Waiting Human | 等待人类 | WAITING_HUMAN |
| Reviewing | 评审中 | REVIEWING |
| Completed | 已完成 | DONE |
| Idle | 空闲 | IDLE |
| Blocked | 已阻塞 | BLOCKED |
| Offline | 离线 | OFFLINE |

总是只有一个 Helix；其编排动作要能在事件里追溯（actor 为系统）。

### 3.9 其它角色：通用座位（Generic Seat）

首批阵容之外的角色（例如 **Workspace Owner / 工作区所有者**、Finance、Legal、Operations、Security 等由 Workspace 自定义的角色）**不得**临时借用上面 8 个角色的形象。它们使用**通用座位**：

- **通用座位是渲染兜底，不是新的固定角色**：不新增角色形象，不新增配饰，不进入官方阵容；
- 形象：共享的 **Operator Base**（无角色配饰），外套为中性色；
- 角色图标：该角色自己的图标（Workspace Owner = 带勾的盾牌；自定义角色 = 工作区配置的图标或首字母徽章）；
- 铭牌、成员徽章、状态环、状态系统与 §6 完全一致；
- 工位：无专属道具的**中性办公桌**；
- 新角色一旦需要专属形象，必须按 §2 的共享设计系统新增，并通过 §8 的验收。

> 这 8 个角色是**官方首批阵容**（冻结顺序：1 Helix、2 Product Manager、3 Architect、4 Frontend Engineer、5 Backend Engineer、6 QA Engineer、7 Reviewer、8 Documentation Specialist）。新增角色必须沿用共享设计系统（§2），并通过 §8 的验收。

## 4. 座位（Seat）模型

```text
Seat = Role 形象
     + Member 徽章（人类：圆形 HUMAN；Agent：六边形 AI）
     + （仅 Agent）模型徽章（中性药丸）
     + 状态环 / 状态字形
     + 当前任务卡（如果有）
```

- **同一个角色多个成员**（例如两个后端 Agent）：生成多个座位，角色形象相同，通过 §5 的有限变体区分，并带编号；
- **人类成员坐在角色座位上**：显示同样的角色形象，成员徽章为圆形 HUMAN，并显示成员显示名（示例：`Member A`）；头像（若有）只出现在组织轨与详情里，不替换画布上的角色形象；
- **座位是空的**（角色没有任何成员）：显示灰色空工位 + “无人负责”标记（对应 `human-channels.md` 的“无人持有该角色 = 阻塞”）。

## 5. 同角色变体（有限）

为区分同角色的多名成员，允许改变：**肤色（6 档）、发色（6 档）、发型（每个角色 2–3 款，保持轮廓测试通过）**。**不允许**改变：服装主结构、配饰、工位、强调色、体型。变体选择是**成员属性**，不影响角色定义。

## 6. 状态系统

### 6.1 八个状态

每个角色**都必须**支持：`IDLE`、`THINKING`、`WORKING`、`REVIEWING`、`WAITING_HUMAN`、`BLOCKED`、`DONE`、`OFFLINE`。

| 状态 | 状态环（线型 / 颜色） | 字形（16 px） | 姿态 / 表情 | 工位 / 画布效果 | 动效（循环周期；静态等价） |
| --- | --- | --- | --- | --- | --- |
| **IDLE** | 细实线环，`IDLE` 灰蓝 | 空心圆 ○ | 放松站 / 坐，neutral | 屏幕暗，桌面整洁 | 无循环；2.4 s 缓慢的“呼吸”仅 1% 缩放（静态等价：无） |
| **THINKING** | 虚线环（点状），`THINKING` 青色 | 三点 ⋯ | 手托下巴 / 看向上方，curious | 屏幕显示“规划线框”，头顶有**三个依次点亮的节点**（不是气泡云） | 三个节点依次点亮，1.6 s 循环（静态等价：三个节点同时半亮） |
| **WORKING** | 实线环 + 旋转的亮弧段，`WORKING` 蓝色 | 齿轮 / 双箭头 ⇄ | 前倾，focus | 屏幕滚动内容；任务卡进度脉冲；后端机架指示灯闪烁 | 亮弧段 1.6 s 一圈（静态等价：实线环 + 进度条） |
| **REVIEWING** | 双线环，`REVIEWING` 紫色 | 对勾内的放大镜 | 手持印章 / 放大镜，focus | 评审线接通到被评审任务；屏幕分栏对比 | 评审线上的光点往返，2.0 s（静态等价：评审线实线） |
| **WAITING_HUMAN** | **琥珀色**实线环 + 外圈虚线，`WAITING_HUMAN` | **人形 + 感叹点**（Human Action 标记） | 抬头看向 Human 区，curious | **Human Action 标记**：琥珀色标记写明“需要的角色 · 成员 · 等待回复 · 已等待 mm:ss”；任务卡右上角琥珀色“等你” | 外圈虚线缓慢旋转，2.4 s（静态等价：外圈虚线静止 + 标记） |
| **BLOCKED** | **红色**实线环 | **红色依赖节点 ✕**（连线断开的节点） | 双手摊开 / 看向依赖线，concern | 依赖边在该处变为**红色节点**（带 ✕）；任务卡显示阻塞原因（上游任务 / 缺失的角色） | 无循环；节点出现时 1 次 200 ms 弹出（静态等价：同左） |
| **DONE** | **绿色**实线环 | **绿色对勾 + 证据角标 ✓n**（n = 证据条数） | 直起身，pleased | 任务卡变绿色丝带；证据托盘展开显示 build / test / review / human 芯片 | 完成时 1 次 320 ms 打勾描边；持续 6 s 后座位回到 IDLE，**任务卡仍保持 DONE**（静态等价：同左） |
| **OFFLINE** | 灰色**虚线环**（`OFFLINE`） | 断开的插头 / 斜线圆 ⊘ | 角色以半透明剪影显示 | 工位断电（屏幕黑、灰色）；铭牌显示原因（执行器不可用 / 通道不可达） | 无动效 |

> **不使用**汗滴、爱心、冒烟等旧式卡通反应作为主要状态语言。表情（5 种）只是辅助，状态语言是**环 + 字形 + 工位 / 画布效果**。

### 6.2 领域状态（DOMAIN STATE）与视觉状态（VISUAL STATE）

**必须区分两层：**

- **领域状态**是系统持久化的事实：`Task.status`（`PENDING / READY / RUNNING / VERIFYING / WAITING_HUMAN / BLOCKED / DONE / FAILED / CANCELLED`）、`Execution.status`、`HumanActionRequest` 状态、成员通道状态等（见 Stage 0 状态机与架构文档）。
- **视觉状态**（本文的 8 个座位状态）是界面**由领域状态与事件上下文推导出的呈现状态**。**它们不一定是新的持久化领域枚举，也不得被实现成新的领域状态。**
- 特别地：`THINKING`、`WORKING`、`REVIEWING` 是**呈现状态**，由 Execution / Task / 事件上下文（例如最近的结构化活动类型）推导；`DONE` 的 6 秒保持与回到 IDLE 是**纯呈现行为**，不对应任何领域转换；`OFFLINE` 由执行器可用性或通道可达性推导。
- 反过来，`WAITING_HUMAN`、`BLOCKED`、`DONE` 与对应领域状态直接相关，但座位上显示的仍是呈现状态；任务卡上显示的才是领域状态本身。

下表给出推导映射（视觉状态 ← 领域状态 / 事件上下文）：

| 视觉状态 | 来源（Stage 0 领域状态 / 事件） |
| --- | --- |
| IDLE | 该座位没有 `RUNNING` 的 Execution，也没有分配给它的未完成任务 |
| THINKING | 座位的 Execution 为 `RUNNING`，且最近的结构化活动是 `thinking` 或 `message`（`ExecutionActivity`） |
| WORKING | Execution 为 `RUNNING`，最近的活动是 `file.write` / `command.run` / `test.run` / `tool.call` / `search` / `file.read` |
| REVIEWING | 任务处于 `VERIFYING`，且该座位（Reviewer）有一个 `RUNNING` 的评审 Execution |
| WAITING_HUMAN | 任务处于 `WAITING_HUMAN`，且存在 `OPEN` / `DELIVERED` 的 `HumanActionRequest`；高亮的是**被要求行动的角色**及由 RoleBinding 解析出的人类成员（见 §6.3），任务所属座位上也显示琥珀色环 |
| BLOCKED | 任务处于 `BLOCKED`（上游依赖失败）；或（未来）工具解析失败导致无法启动 |
| DONE | 任务处于 `DONE`（只能由 `evaluateCompletion()` 的通过判定到达，证据已记录） |
| OFFLINE | 执行器检测不可用（`check()` 为否），或人类成员的所有 `MemberChannel` 为 `unreachable` / 无已验证通道 |

**不在 8 个座位状态里的任务状态**：`PENDING` / `READY`（任务卡显示为“排队”灰色丝带，座位保持 IDLE）、`FAILED`（任务卡红色实心 ✕ 丝带 + 重试标签；座位回到 IDLE 或进入 BLOCKED 取决于下游依赖）、`CANCELLED`（任务卡划线灰）。

### 6.3 WAITING_HUMAN 的一等视觉模型

`WAITING_HUMAN` 是**一等产品视觉状态**。它必须呈现五件事：**琥珀色环**、**Human Action 图标**、**负责的角色**、**已等待时间**、**需要的动作**。示例（Human Action 卡片）：

```text
WAITING HUMAN
Required role:   Workspace Owner
Action:          Approve requirement
Waiting:         00:12:40
Candidates:      Human Member(s) bound to this role
```

规则：

1. 呈现链路固定为：**Role → RoleBinding → Human Member → Human Action**。卡片先写**角色**，再列出该角色下由 RoleBinding 解析出的**人类成员**；
2. **不得悄悄把动作指派给“随机的某个人”**：候选成员只能来自 RoleBinding；如果角色没有人类成员，卡片显示“无人负责 / No Human Member bound”（阻塞），而不是任意分配；
3. 动作名称使用架构定义的人类动作（通过 / 拒绝 / 接受 / 退回返工 / 无法承接 / 评论），授权来源写作“**该审批门的授权人类成员 / authorized Human Member for this gate**”；
4. **本阶段不包含任何 Telegram 专有界面**（通道只以一个中性的“通道状态”小标记出现，且原型中标注为模拟）。

### 6.4 优先级（同一座位同时满足多个条件时）

`OFFLINE` > `BLOCKED` > `WAITING_HUMAN` > `REVIEWING` > `WORKING` > `THINKING` > `DONE`（仅在 6 秒保持期内）> `IDLE`。

### 6.5 无障碍

- 每个状态都有**文字等价**（中英文），写入工具提示与屏幕阅读器标签，例如：`后端工程师（AI · Codex）：工作中，任务 TASK-213`；
- 状态**永不只靠颜色**；
- `prefers-reduced-motion`：所有循环动效替换为静态等价形态（表中最后一列）。

## 8. 验收（角色系统）

1. 8 个角色的纯色剪影在 **48 px 高**下**互不混淆**（评审用灰度剪影表）。
2. 每个角色提供：轮廓、服装、配饰、角色图标、强调色处理、工位的完整定稿，并**一致地**使用共享设计系统（线条、着色、面部、服装层）。
3. 8 个状态 × 8 个角色**全部**有可识别的视觉，**状态不依赖颜色**，且每个状态都有静态等价形态。
4. 没有以模型命名的角色；换模型不改变形象；模型徽章为中性药丸，无厂商品牌色。
5. 人类座位与 Agent 座位在 48 px 下可以通过徽章形状区分。
6. 没有汗滴 / 爱心 / 冒烟 / 猫耳 / 牲畜元素；粉色面积（前端强调色等）符合上限。
7. 性别中性：不存在“男版 / 女版”的服装分叉；评审时由多人独立判断，无明显性别刻板印象。
8. 每个状态变化都能对应到 §6.2 的真实数据来源；没有无来源的装饰动画。
