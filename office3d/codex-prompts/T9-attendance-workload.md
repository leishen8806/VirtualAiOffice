# T9-attendance-workload：考勤与工作量统计，为「增减岗位」提供依据（只出建议，不自动动人）

先读 `_common.md`。**本任务的例外规则：** 允许新增 `workload.mjs`、`tests/workload.test.mjs`；允许修改 `stats.mjs`（**只限**为本任务补记数据，不得改已有字段含义和现有统计口径）、`server.mjs`（**只限第 5 节接线**，不要碰局域网访问码、`hostOk`、大屏令牌、`act()` 已有分支、静态文件白名单）、`ui.js`（「治理」弹窗里加一节「编制与工作量」）、`README.md`。**不要改** committee / standup / acceptance / blocked / memory / wall 等业务模块。**不得向 Paperclip 发任何写请求**（本功能全程只读 Paperclip；唯一写入是本地 `workload.json` 和 `knowledge` 之外的 `office3d` 目录文件）。**不得自动招聘、解雇、暂停、改派任何岗位**——输出的只是给董事会看的建议。不新增依赖。改前备份到 `office3d-backup-workload`。

【背景】董事会要求用「考勤和工作量统计」来决定减少或增加岗位。现有账本 `stats.json`（`stats.mjs`）记录了每个岗位的运行（成功 / 失败）、完成任务、评论，但只有 5 天，且没有「出勤」「空闲」「排队」的概念。我已用现有账本做过一次试算（5 天、25 岗位）：运行次数从 80 次（OpsLead）到 0 次（Frontend1、React1）差异巨大。**但差异主要由任务怎么派来决定，不一定反映岗位有没有价值**（审查类、架构类岗位只在有任务来时才工作；晨会每人每天最多 2 个任务）。所以统计必须把「没活干」和「干不动」区分开，并且**数据不足时必须明说「不足以判断」，不得给出增减结论**。

## 1. 指标定义（先写进 `README.md` 和 `workload.mjs` 顶部注释，口径要可核对）
对每个岗位、每个**上班日**（读 `../workhours/workhours.json`，周日也上班）：
- **出勤**：当天该岗位**可用**——状态不是 paused / error / terminated，且当天上班时段里至少有一个时刻是 idle 或 running。暂停 / 出错的天数单独记「不可用天」，不算缺勤也不算空闲。
- **有产出日**：当天至少有一次成功的运行，或完成了一个任务。
- **运行次数 / 成功率**：成功 / 失败 / 超时 / 取消分开记；取消不算失败（沿用 T4 `isFailure` 的口径，复用不要另写）。
- **完成任务数**、**评论数**：沿用账本。
- **忙碌时长**：运行的累计时长（`startedAt` → `finishedAt`），按当天上班时段裁剪；只用真实时间戳，没有就记「未知」，不估算。
- **利用率** = 忙碌时长 ÷ 当天上班时长（9 小时）。
- **队列压力**：该岗位名下 `todo` / `in_progress` / `in_review` / `blocked` 的任务数（取每天 08:30 和 17:00 两个时刻的快照，写入 `workload.json`；Paperclip 接口没有历史快照，只能从现在开始积累，**不要用当前状态倒推历史**）。
- **等待时长**：任务从 `todo` 到第一次运行的间隔中位数（只用任务和运行的真实时间戳）。
- **返工次数**：任务评论里「【第 N 轮退回】」的条数（流程第 6 节的格式）。
- **阻塞占比**：该岗位名下任务处于 `blocked` 的比例。

## 2. 窗口与可信度
- 默认窗口：最近 14 个上班日；同时给最近 7 个上班日作对比。
- **可信度分级**（页面每个岗位都要显示）：有效观察天数 ≥14 → 「可用」；7–13 → 「参考」；<7 → 「不足以判断」。**「不足以判断」的岗位不得出现在任何增减建议里**。
- 账本从 2026-10-15 开始，所以 2026-10-29 之前所有岗位至多是「参考」，这是预期结果，测试里要有这个用例。
- 「队列压力」快照从功能上线日开始积累，积累不足 7 天时，涉及队列的规则一律不触发，并在页面写明「快照积累中（第 N 天）」。

## 3. 建议规则（只生成建议和证据，阈值放 `workload.json` 的 `thresholds`，可调；默认值如下，页面必须显示用了哪些阈值）
**建议增加岗位（扩编）**，同一岗位或同一类岗位（同职能、同项目）同时满足、且可信度 ≥「参考」：
- 利用率 ≥ 70% 的上班日占比 ≥ 60%；
- 且队列压力：下班快照里 `todo` ≥ 3 的天数占比 ≥ 50%，或等待时长中位数 > 4 小时；
- 且不是因为失败重跑造成的忙（成功率 ≥ 70%）。失败率高的先建议「排查」，不建议扩编。
**建议减少岗位（缩编 / 合并）**，同时满足、且可信度 =「可用」：
- 有产出日占比 ≤ 20%，且利用率中位数 ≤ 5%；
- 且**同期没有队列**（它的队列压力和同类岗位的队列都为 0）——即不是因为任务没派给它；
- 且存在可承接其职责的同类岗位（给出候选，来自同职能）。
**建议排查（不增不减）**：失败率 ≥ 30%；阻塞占比 ≥ 50%；返工次数多；长期 error / paused。
**资金类岗位**（GoSenior / DBEngineer / LedgerAuditor / SecurityReviewer 与账务相关岗位）：只给数据，**不给缩编建议**（审查链必须保留），扩编建议要标「需董事会审批」。
- 每条建议都要带：岗位、结论类型、可信度、触发的每个条件的**实测数字**、窗口、数据缺口说明。**不得写「预计」「应该」这类推算，只写事实和规则命中情况。**
- 规则命中 ≠ 必须执行：页面和报告里明确写「建议仅供董事会决策，招聘 / 缩编需董事会批准」。

## 4. 产出
1. `workload.json`：每日聚合账本（岗位 × 日期 → 上述指标）、队列快照、阈值、最近一次报告；**原子写入**，损坏时不崩溃（视为空账本并在 `/state` 提示）。
2. **周报**：每周一 08:20（上班前）生成 `E:\VirtualAIOffice\paperclip-ops\office3d\reports\workload-YYYY-Www.md`（目录不存在则建；已存在不覆盖，加 `-2` 后缀）：岗位表（出勤天 / 不可用天 / 有产出日 / 运行 / 成功率 / 利用率 / 完成 / 返工 / 队列 / 等待 / 可信度）+ 建议清单 + 数据缺口。**只写标题和数字，不写任务正文**；金额、IP、邮箱、密钥走 `redactText`（复用 `wall.mjs` 的口径）。
3. 不向 Paperclip 发评论、不新建任务；Telegram 通知董事会一次「本周编制报告已生成」+ 报告路径 + 建议条数（用现有 `notify`，同一份报告只通知一次；通知里**不含**岗位级结论细节）。
