# O1-office-redesign-plan：办公区扩大 + 中央圆形茶水吧台 + 四角分区——重新规划（只出规划与检查脚本，不改场景，约 1.5 小时）

**执行者：Codex（新会话）。办公室场景规划（主线展示层，**风险高：25 位同事的工位、路径、会议、巡检都依赖它**）。** 先读：`_common.md`、`_lane-town.md`、`office-layout.js`（**全文**：`ENVELOPE / CORRIDORS / OFFICE_ROOMS / SEATS / BOSS / BOARD_TABLE / MEETING_ROOMS / RECEPTION / ENTRANCE / FOYER_* / LOUNGE_* / REGION_FOCUS / PLAZA / MINI_BOUNDS` 及全部路径函数）、`docs\foyer-plaza-plan.md`、`docs\dr-warehouse-plan.md`、`director.js`、`fun.js`、`cat-play.js`、`pedestrian-*.mjs` 与它们的测试，以及 `前厅与小镇规划.md` 第一～二十五节（**尤其「保留中轴上的前台」「前厅 / 广场已有决定」**）。

**董事会 2026-10-21 决定（原话）：** 「办公区再扩大一点；仓配园区迁移到左侧公路的另一侧单独做仓配园区。这个办公区的最中间，做成一个圆形的茶水吧台区吧，然后往 4 个角分办公区。」

**允许新增：** `docs\office-redesign-plan.md`、`docs\office-redesign-checks.mjs`；`README.md` 追加一节「办公区重新规划（O1）」。**不要改**任何已有代码文件（`office-layout.js`、`app.js`、`env.js`、`director.js` 等）、`server.mjs`、`town\`。**不对 Paperclip 发请求；不需要重启服务。**

## 不可破坏的约束（逐条在规划里对照）
1. **业务流程独立运行**：办公区是「办公室 3D 的工作视图」，改版**不得**影响任务、审批、治理中心、`/state`、对话、巡检的任何逻辑；所有「同事在哪个区域」只是展示，**区域的 id（`product / eng / quality / drlife / board / kb / ops / review / plan / lounge`）与点击、搜索、`REGION_FOCUS`、治理中心的跳转目标必须保持不变**（可以换位置、换形状，不得改 id、不得删区域）。
2. **25 位同事、工位总数与分配不变**（`SEATS` 的人员 → 区域映射不变，只允许坐标变化）；董事会席、会议室 A / B（评审室、计划室）、老板桌、知识中心、运维办公室、Dr.life+ 工作室、质量与安全、产品与设计、工程办公室全部保留。
3. **前台保留在中轴**（`RECEPTION`，沿用 `CORRIDOR_X` 中轴与 `bypassX` 绕行），**入口、前厅服务台、访客与等候区、DR 广场入口**保留；入口仍在南侧，与 DR 广场的关系不变（广场可随办公区南移，但不得改 `PLAZA` 内部：中央圆、摊位、咖啡车、队列、等候座位）。
4. **新中心：圆形茶水吧台区**——办公区**几何中心**（建议以新 `ENVELOPE` 的中心为圆心）一个**圆形吧台**（直径建议 6–8 m，**你给出推荐值与理由**），吧台外圈有座位 / 站位；原有休闲区 `LOUNGE_*`（沙发 / 咖啡）**并入或围绕它重新安排**，不得消失。
5. **四角分区**：从中心向四个角划分办公区。**你给出分配方案（至少两个备选）**：哪些部门放哪个角（建议原则：董事会 / 评审室 / 计划室等「会议与决策」成组；工程 / 质量 / 运维等「交付」成组；产品与设计 / Dr.life+ / 知识中心等「创意与知识」成组；老板桌的位置）；每个角的外框、墙、门、走廊。
6. **走廊与动线**：重新规划**主走廊（十字或环形）**，保证 ① 任意工位到任意工位、到前台、到会议室、到休闲区的路线存在且不穿墙；② 25 人上班 / 下班 / 会议 / 评审 / 董事会 / 消费（前厅与广场）/ 小橘公共路线全部**重新生成并无碰撞**；③ 不改变 `corridorPath / officeExit / officeTrip / meetingTrip / loungeTrip / consumerTrip` 的**函数签名与返回形状**（内部可改）。
7. **扩大幅度**：「再扩大一点」——给出**三档**（建议 +15% / +25% / +35% 的建筑面积）的外框、与现有 `ENVELOPE x -44…22, z -13…13`（66×26 m）的关系、对 `PLAZA / FOYER / MINI_BOUNDS / 环境铺装（112×88）/ 树 / 路灯 / 道路` 的影响；**推荐一档**，说明理由。
8. **仓配园区迁出**：现有 `WAREHOUSE / DOCK / PARKING / WEST_WALK / SERVICE_PASSAGE / CAMPUS_PAVING / LOGISTICS_GATE_ZONE / WAREHOUSE_ITEMS / WAREHOUSE_FOCUS` 以及 `warehouse-shell.js` 将**迁到西侧公路（`x≈-64`）的另一侧**，作为独立仓配园区（见 `S2-0c-dr-campus-plan.md` 的更新）。规划里**列出迁出后空出来的区域**（`x -46…-10, z 13…35.5`）如何处理（绿化 / 扩大广场 / 办公区扩建用地），**和迁出所需修改的常量、测试清单**（只列清单，不施工）。
9. **默认不破坏现状**：新布局必须能在**开发期以 URL 参数 `?layout=2`** 并存检查，验证通过后再切为默认；**旧布局在切换前保持可用**（规划里写清楚如何做到：`office-layout.js` 的版本化方式、`app.js` 最小接线、测试如何同时覆盖两套）。

3. **圆形吧台设计**：圆心、半径、吧台环、座位数（建议 ≥ 8）、出入口（环形需留 ≥ 2 个 ≥ 1.2 m 的缺口，供通行与服务）、与休闲区合并方案、**咖啡互动（小橘 / 同事）的站位与路径**；碰撞体的拆分建议（圆形碰撞如何用现有 AABB 近似：**给出近似方案与误差**）。
4. **迁移与施工分期**：拆成**每张约 1 小时**的任务卡草案（建议编号 `O2…`）：常量与数据 → 墙与地面 → 工位与家具 → 路径与碰撞 → 吧台 → 前厅 / 广场联动 → 仓配迁出 → 切换默认；每张写：改哪些文件、前置、**绘制调用预算**、是否改 `app.js`（**互斥**：排在 A4、A5a 之后或明确错开）、验收（含 **T16b 200 种子压力、25 人全路线、小橘、会议、董事会、前厅消费全部 0 穿墙**）。
5. **性能与画质**：总 calls / 三角形 / 光源预算（高 / 低档）；圆形吧台与新增墙面必须走合并 / 实例化；**不得新增光源**；与 `quality.js` 现有机制配合；**必须避免 z-fighting**（新增贴墙薄件前表面偏移 ≥ 0.12 m；参见 S2-2b）。
6. **隔离与安全**：零 token、不写 Paperclip、故障只降级自己、`?layout=2` 之外的页面与改动前逐字节一致；不涉及 DR 币。
7. **检查脚本 `docs\office-redesign-checks.mjs`**：对**规划坐标**做自动检查（不改任何已有文件）：区域互不重叠、id 全部保留、工位 25 个且各在其区域内、每个工位到前台 / 会议室 / 休闲区 / 出口**可达**、走廊净宽 ≥ 1.2 m、吧台缺口宽度、门洞宽度、坐标对齐 0.5 m、与 `PLAZA` 内部无重叠；**带 `OFFICE_REDESIGN_CHECK_MUTATE=overlap|blocked|lostid` 的故意破坏开关，证明检查会失败**；最后输出 `SUMMARY … result=PASS`。

## 补充（2026-10-21 董事会追加，**纳入本规划**）：新增 4 个「展示部门」
董事会原话：「区域增加了之后，增加展示部门：市场部、营销部，客服部，售后（这些部门可以只做展示，人物也只做展示，偶尔去休息室走动走动即可）」。

**定位：纯展示。** 这 4 个部门的区域和人物只用于让办公室看起来是一家完整的公司，**不是 Paperclip 里的真实同事，不承担任何任务**。要求：
1. **区域**：新增 4 个区域，id 建议 `market`（市场部）、`marketing`（营销部）、`service`（客服部）、`aftersales`（售后部）；中文名如上；**与现有 id 不冲突**；**不进入治理中心的「同事 / 任务」列表**，不得出现在任何会改变业务含义的位置（`/state`、审批、预算、搜索结果里的「同事」）。点击 / 聚焦（`REGION_FOCUS`）可以有，镜头聚焦即可，**面板里必须明确标注「展示部门 · 模拟角色」**。
2. **人物**：每部门建议 3–4 个**展示人物**（总数你给建议，**不得超过 16 个**以守住性能预算），**不使用真实同事的名字 / 头像 / 工号**；**与 25 位真实同事外观上能区分**（例如统一的「模拟角色」标识牌 / 小标签「模拟」，遵守「三类人物标识」：工作 Agent / 真人 / 生活 NPC 必须能区分，NPC 标明「模拟角色」）。
3. **行为（零 token 脚本）**：在各自工位「坐着 / 简单办公姿态」，**偶尔**（低频，错峰，建议每人每小时 0–2 次）走去休息室 / 圆形茶水吧台再回来；**全部是确定性脚本，不调模型、不读 Paperclip、不发评论 / 任务、不写进同事上下文**；路径必须走现有走廊与碰撞系统，**不得穿墙、不得堵门、不得进入会议室与董事会**；人物数量与走动频率有**上限与开关**（`display-staff.json`，**默认关闭**，缺失 / 损坏 / 非布尔 `true` 一律关闭；关闭时画面里这些人物不创建，**区域家具可保留或关闭，你给方案**）。
4. **性能**：展示人物走 **实例化 / 简化骨骼 / 可见性分级**（低档只显示坐姿静态或隐藏），写明**新增 calls 与三角形预算**；高 / 低档分别给上限；**不得新增光源**。
5. **与既有规划的关系**：展示人物 ≠ 生活 NPC（NPC1 / NPC2 另有任务卡，用于小镇街区 NPC）；这里只规划**办公区内的展示人物模块**（建议独立模块 `display-staff.js` + 纯逻辑 `display-staff-logic.mjs`），**不复用也不修改 `director.js` 对真实同事的调度**；与 T16b 压力测试并存（展示人物进入路径压力测试，200 种子 0 穿墙）。
6. **文案红线**：展示部门**不得被描述成真实部门或真实员工**；不出现真实商户 / 真实客户 / 真实联系方式；不涉及 DR 币。

**因此规划里需要多回答：** 四个新部门放在四角里的哪里（或在四角外环 / 沿边布置）、各自面积与工位数；休息室 / 吧台离它们的走动路径与时间预算；`display-staff.json` 的开关设计；展示人物的新增 calls 预算。检查脚本也要覆盖：新区域不重叠、id 不冲突、展示人物工位在各自区域内、展示人物到吧台可达。
