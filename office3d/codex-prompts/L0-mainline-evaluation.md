### A. Paperclip 原生能力评估（对应盘点文档第四节 6 项）
1. **authenticated 部署模式**：如何启用（配置项、命令，**只读不执行**）、启用后的**人类角色与权限模型**（有哪些角色、能否按公司授权、能否限制到只读 / 只能看自己公司）、是否有**邀请 / 注册流程**、是否支持**会话 / 令牌**、对本机 `local_trusted` 下现有 Agent 与 CLI 的影响（Agent 心跳是否仍可用、需要哪些 API key）；评估「别家老板登录能否直接用 Paperclip 原生认证，而不是我们 M5-2 的自建认证」的**可行性、风险、迁移成本**，给出明确建议与**需要董事会决定的点**。
2. **多组织隔离强度**：从源码与路由层面确认：资源路径是否都带 `companyId`；服务端是否**校验调用者与公司的关系**（local_trusted 下是否形同虚设）；用公司 A 的 id 请求公司 B 的资源会怎样（**只读推断；目前只有一家公司，无法实测的写「需要测试公司」并写出需要的测试用例清单**）。
3. **隔离执行工作区与密钥注入**：工作区类型、是否 git worktree、**进程 / 文件系统隔离到什么程度**（能否限制 Agent 只访问某个目录；能否阻止读其它公司的工作区 / 密钥）、密钥如何注入与是否会出现在日志 / 运行记录里；结论：**外部公司的 Agent 在我们这台机器上跑代码是否安全**，以及 V1 试点档需要补什么。
4. **预算与硬停**：预算字段（公司 / 同事 / 项目）的语义、**何时拒绝运行**（硬停 vs 仅告警）、`budgetMonthlyCents / spentMonthlyCents` 为什么一直是 0（成本状态 `unpriced`？）、暂停 / 恢复同事的 API 形态（**只读，不调用**）。
5. **用量缺失 18.5%**：统计最近全部运行里 `usageJson` 各字段的缺失模式（按适配器 / 模型 / 状态 / 是否被取消分组），找出原因的线索（是哪类运行缺失、是否为最近才缺失），给出补齐或隔离的建议。
6. **任务契约的承载方式**：Paperclip 的任务 / 项目 / 目标 / 执行策略 / 工作产品 / 自定义字段 / 插件里，哪些可以承载「范围、禁止事项、依赖、验收标准、预算、责任人、交付物」；**能不能不改内核就做到「缺字段则不让开工」**。
