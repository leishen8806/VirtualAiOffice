# T13c-rework-rounds-from-fix：修复轮次也算返工轮次（原任务名下只有「第 N 轮修复」时也能数到轮次）

**例外规则：** 只允许修改 `rework.mjs`、`tests/rework.test.mjs`、`README.md`（T13 章节里补口径说明）。不要改 `server.mjs`、`ui.js`、`governance.mjs`、`acceptance.mjs`、`standup.mjs`。**不得向 Paperclip 发任何写请求。** 备份到 `office3d-backup-rework-fixrounds`（办公室目录没有 Git）。改的是服务端模块，**让人重启服务**（汇报里写明，不要自己结束进程）。

## 背景（真实数据）
我们的实际流程里，评审员常把「【第 N 轮退回】」写在**审核任务**（CMP-282、CMP-295、CMP-297）上，被审的**原任务**（CMP-278）名下只有执行者写的「【第 N 轮修复】」。现在的实现只用「退回」评论算 `rounds`，所以 CMP-278 虽然评论里出现过 `【第 1 轮修复】`、`【第 2 轮修复】`、`【第 3 轮修复（董事会例外已批准）】`、`【第 3 轮修复】`，`rounds` 却是 0——**原任务的返工超限保护数不到轮次**。

出现「第 N 轮修复」就说明已经被退回过 N 次，所以轮次应取两者较大值。

## 要求
1. **`rounds` = 退回评论里的最大轮次 与 修复评论里的最大轮次 中较大的一个。** `capped`、`warned` 仍按 `rounds` 判定（`capRound` 默认 3、`warnRound` 默认 2，不变）。
2. 复验（`第 N 轮复验`）**不参与**这次口径（本任务不改它，避免范围扩大）；它仍只用来更新 R 项状态。
3. **识别规则不能放宽，要沿用 T13b 的严格标题规则**：标题必须在行首（允许 Markdown 前缀）并被 `【…】` 或 `[…]` 括起来；正文中间的「提到」一律不算。**修复标题要新增一种容忍**：括号里允许在「第 N 轮修复」之后带一段括注，如 `【第 3 轮修复（董事会例外已批准）】`（真实评论里出现过），括注内容不影响识别，括注不得吞掉轮次数字。
4. **修复评论没有对应的退回评论时，R 项也要建立**：修复行形如 `R4 ｜ 修复：… ｜ …` 或 `R5 ｜ 已修正 ｜ 复验：…`，R 项状态按行内「状态：已修 / 未修」判定；没有「状态：」字样但含「已修正 / 已修复 / 已修」的按已修（`fixed`），含「未修」的按未修（`open`），都没有的按 `open` 并在 `formatIssues` 记「修复缺状态」。不要因此伪造退回条目的「对应 AC / 复现」信息（那只在退回评论里检查）。
5. 修复评论里**没有任何 R 项**时：仍然计入轮次（标题行本身就说明发生了第 N 轮修复），但在 `formatIssues` 记「修复缺 R 项」。
6. 视图和巡检评论的措辞要如实：`view().tasks[].rounds` 保持数字；新增 `roundsSource: 'return' | 'fix' | 'both'`（轮次来自哪类评论）；巡检评论正文把「已退回到第 N 轮」改为「已进行到第 N 轮返工（依据：<退回 / 修复评论>）」。**不要改动发评论的条件**（只在 `capped` 且未结束且未发过时发）。
7. 其余行为不变：程序评论（含 `【返工巡检】`）不计数、作者必须是 agent 或董事会、中文数字、缺 AC / 缺复现、R 编号重排与复用、同项重复、`isCappedView`、`ignoredMentions`。
