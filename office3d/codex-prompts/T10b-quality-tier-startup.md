## 已知情况（我读代码和实测发现的，**务必先验证再动手**）
1. **`prepare()` 才构建 medium / low 两个「场景变体」**（`buildVariant`：把静态网格按材质与 12×12 米格子实例化 / 合并，生成 `quality-medium`、`quality-low` 两个副本），而 `prepare()` 要等首个 `/state` 数据之后约 2.5–6 秒的静态合并完成才调用。**在 `prepare()` 之前，任何画质档渲染的都是完整的原始场景**（约 2000 个网格 / 上千次绘制）——也就是弱机上**最需要减负的开机阶段反而最重**。`?q=low` 或 localStorage 里是 low 的用户，开机阶段仍先画一遍重场景。
2. **`prepare()` 一次性为 low / medium 两个变体都做 `buildVariant`，并对 `['low','medium','high']` 依次 `apply(q); renderer.compile(scene, camera)`**——三次着色器编译 + 两个变体构建集中在同一帧附近，是一个很长的主线程停顿（我实测 `metrics.renderMs` 曾读到 1406 ms）。当前档位用不到的变体和编译应当推迟 / 分摊。
3. **测量陷阱（本任务第一步就要解决）**：(a) 浏览器面板 / 标签页**不聚焦或被遮挡时 rAF 被限速或暂停**，`metrics.fps = 0`，`renderer.info.render.calls` 是**旧的一帧**，读数会骗人；(b) 手动调用 `renderer.render()` 会把**阴影 pass 的 calls 一起计入**，与页面真实帧的口径不同；(c) `window.__office.quality.select(q)` 会**重载页面**（不是热切换），测完要看是否有残留状态。**你必须先建立一套可信、可复现的测量方法并写进 README 与汇报**（建议：用你自己的 Playwright Chrome 以 `?q=low|medium|high&perf=1` 加载，**保持页面聚焦 / 用 `page.bringToFront()`**，等首帧后以页面自己渲染循环里记录的 `renderer.info`（在渲染循环末尾读取，而不是外部手动 `render`）为准，分别记录「含阴影 pass」与「主 pass」的 calls，并明确哪个是验收口径）。
4. **S1 之后场景变大了**：前厅 / 广场新增约 32 个原始网格（`foyer-*`），`app.js` 还有新的动态面板贴图、等候 / 消费点人物行为。T10 当时验收的数字（medium ≤ 900、low ≤ 500、灯数、DPR）**必须在当前场景上重测**，不得沿用旧结果。
5. **T10 验收时「逐档运动实测」没有做完**（我当时标注为未验证）：低档下的人物走路 / 访问消费点 / 等候 / 休息区 / 会议 / 小橘 / 点击拾取 / 小地图，是否仍然正确，没有逐档验证。

## 要做的事
### 1. 先建测量基线（第一步，**先于任何改动**）
按已知情况 3 的方法，在**当前代码**上测出并存档（`office3d-backup-t10b\baseline.json` + 汇报表）：三档（`?q=low|medium|high`）× 三个机位（默认镜头、前厅、DR 广场）× 两个视口（1280×720、390×844）的：`calls`（主 pass / 含阴影 pass）、`triangles`、灯数、阴影状态、DPR、**首帧时间**（从导航开始到第一次渲染）、**加载期最长主线程停顿**（用 `PerformanceObserver` 的 `longtask` 或 CDP 记录，列出前 5 个）、加载完成时间。**如实写**哪些数字取不到。
### 2. 变体更早构建、按需构建（核心）
- **已知档位时开机即用对应档位**：`?q=` 强制、localStorage 已有选择、大屏（`?wall=1` 默认 high 不变）时，**在首次渲染原始重场景之前**就让该档位生效：要么把 `capture + 对应变体构建` 提前到首次渲染之前（场景构建完成、`/state` 数据到达之前就可以做，**静态网格合并**如果必须等数据，就让合并前的重场景**尽量不渲染**：例如保持加载遮罩 / 低分辨率占位帧，**但不得出现白屏 / 黑屏闪烁或加载时间明显变长**）；
- **只构建当前档位需要的变体**：low 用户不构建 medium 变体（反之亦然）；`high` 用户（原始场景）**两个变体都不构建，直到空闲时或用户切档时**；其余变体放到 `requestIdleCallback`（带 `timeout`）或按帧分摊（每帧限时，例如 ≤ 8 ms），**不得一次性长停顿**；
- **着色器编译只编译当前档位**；其他档位的灯集合 / 材质编译推迟到空闲，或在手动切档时一次完成（切档前给 `加载中` 提示，避免无反馈的卡顿）；`apply()` 的行为与现有一致（灯集合、阴影、材质、实例化切换），**不得改变各档位最终的画面与数字目标**；
- **warmup 自动选档（没有记录的新用户）**：现在是先按 `medium` 开始、6 秒预热后依据帧耗时 + 设备信号选档；保留这个逻辑，但**开机即用 `medium` 变体（而不是原始重场景）**，预热期的帧耗时统计要**排除**构建变体 / 编译造成的那几帧（否则会被自己的卡顿误判为弱机而降档）。给出你的排除方法与测试。
### 3. 启动阶段卡顿治理（弱机首屏）
- 目标（**在 4× CPU 降速的 Playwright Chrome + SwiftShader 上实测**，真机拿不到要如实写「代理」）：加载期**没有任何单个主线程任务 > 300 ms**（列出剩余超标项和原因）；`low` 档首次可交互时间（能转镜头）比基线缩短，写出前后数字；
- 排查并减轻启动期的其它大头（先实测再动手，**逐项写前后数字，没做的写原因**）：纹理上传（>1024 的在 low 降采样已有，确认也适用于启动阶段）、GLB 解析、大量同步的 `new THREE.Mesh` 构建、同事人物 26 个骨骼模型的创建、`mergeStatic` 本身的耗时；可以考虑把部分工作切片到多帧，但**不得改变最终场景内容与碰撞注册**。
### 4. 逐档运动与交互实测（补 T10 欠的验证）
**三档各做一遍**（`?q=low|medium|high`，Playwright 保持页面聚焦；需要推进时间用 `window.__office.step(dt, n)`；**不创建任务 / 提问卡**，真实的待回答事项若存在就用它，没有就写「未验证」）：
- 25 位同事各就各位；同事互访（任意两人走一趟，用现有事件调试入口 `enqueue` 或 `debugMeeting` 之类**只在页面内存里**触发，不写 Paperclip）；去休息区；会议室 / 评审室入座；董事会找苏晨；
- **S1 新增**：消费点访问（`director.visitConsumer`：用 `window.__office.director` 直接对一位空闲同事触发一次去咖啡吧、停留、返回，**页面内存里模拟**，不写任何服务端状态；`mode:'waiting'` 等候人物若 S1-5b 已落地也测）、排队六人同点；
- **小橘**：走路、跳桌、被逗（`catToggle / catAim`）；低档下假阴影 / 实例化是否影响它；
- **拾取与点击**：点击同事 / 点击家具 / 点击地面走路 / 小地图跳转 / 搜索跳转，在 **low 的实例化 / 合并变体**下是否仍命中正确对象（实例化网格的拾取是已知风险点：`mesh.userData.instanceSources` 的映射是否被拾取逻辑使用）；
- **碰撞**：`furnitureCollision` 用原始几何，确认低档变体不会让人物穿过家具或被隐形东西挡住（用 T16b 的 harness 思路在三档下各跑 20 个种子即可，**不要求 200 个**）；
- **切档**：高 → 低 → 高：**刷新后保留**；手动切档因重载页面，写明行为；确认没有残留状态（旧的假阴影、灯、DPR、阴影状态）；
- **视觉**：三档在默认 / 前厅 / 广场机位各一张截图（Playwright 截图，同视口），列出 `low` 相比 `high` **视觉上丢了什么**（逐条，不要「基本一致」这类话）。
### 5. 预算复核与回归
- 在**当前场景**上复核 T10 的数字目标：`medium` calls ≤ 900、灯 ≤ 8、DPR ≤ 1.25；`low` calls ≤ 500、灯 ≤ 4、无实时阴影、DPR ≤ 1、帧率上限 30；`high` 不得退化（calls 与基线相比增量 ≤ 5%）。**以第 1 步确定的口径为准**；如果 S1 之后某档**确实超标**，说明超标的来源（哪些类别的网格 / 哪些新增物体），并在本任务内用既有手段（实例化 / 合并 / 剔除 / 灯光）修到达标；修不到的**如实写**，不要放宽目标。
- 页面隐藏时完全暂停渲染、可见但静止时降到 10 帧、大屏嵌入模式（`?wall=1`）默认 `high`——这些 T10 的行为保持，并各有一条测试或实测证据。
