【董事会已定的 4 条】
1. **由 KnowledgeKeeper 审核入库**：同事提交的经验条目先进「待审」，KnowledgeKeeper 审核后才进正式库。
2. **任务开工前，程序按任务关键词自动检索知识库，把最相关的 3 条摘要放进任务提示里。**
3. **范围：项目和流程知识，也包括每个同事的个人工作笔记。**
4. **密钥、账务数据、服务器地址不进记忆库，写入前自动扫描拦截。**

## 1. 目录与条目格式（`E:\VirtualAIOffice\knowledge\记忆\`，本地 git，没有远端）
- `待审/`：同事提交的条目，每条一个文件 `YYYYMMDD-HHMM-<岗位>-<短名>.md`。
- `项目/`、`流程/`：审核通过的正式条目。
- `个人/<岗位名>/`：该岗位的个人工作笔记（审核通过后入库）。**个人笔记只给本人用**：检索时只有该任务负责人本人的个人笔记才会参与。
- `已驳回/`：KnowledgeKeeper 驳回的，文件头记原因，保留 30 天后可清。
- `归档/`：过期、长期没人用、被取代的条目（不进索引、不检索，历史仍在 git 里），见第 8 节。
- 条目格式（前置信息 + 正文，正文 ≤ 800 字，超出视为不合格）：
  ```
  ---
  title: 一句话标题
  type: project | process | personal
  author: 岗位名
  source: CMP-xxx          # 必填，来源任务编号；没有来源的不收
  tags: [关键词, 关键词]
  created: 2026-10-19
  status: pending | approved | rejected
  expires: 2027-01-19      # 可选；过了期限不再被检索，但不删除
  ---
  正文：结论 / 为什么 / 怎么做 / 适用条件。写事实，别写推理过程。
  ```
- 目录和 `.gitkeep` 由程序在首次启动时创建（只建目录，不动已有文件）。

## 2. 写入前扫描（硬规则，先做这一块，最重要）
`memory.mjs` 导出 `scanMemoryText(text)`，命中任何一类就**拒收**并给出原因（只给类别和位置，**不回显命中的值**）：
- **密钥类**：Telegram bot 令牌格式（`\d{8,10}:[A-Za-z0-9_-]{30,}`）、`sk-`/`ghp_`/`AKIA`/`xox` 等常见前缀、PEM 私钥头、40 位以上连续字母数字串、`password|passwd|secret|token|api[_-]?key|accessPassword|sessionSecret` 后面跟赋值的内容。
- **服务器地址**：IPv4（含私网）、`*.khmerx.org` 及其它带真实域名的 URL、`ssh ` 命令里的主机；`localhost` / `127.0.0.1` / 文档示例域名（`example.com`）放行。
- **账务数据**：金额带币种符号或单位（`$`、`¥`、`USD`、`元`、`KHR` 等跟数字）、银行卡 / 账号（连续 12 位以上数字）、`余额|提现|入账|流水号` 后跟具体数字。
- 复用 `server.mjs`/`wall.mjs` 里已有的 `redactText` 口径，**不要另写一份不同的规则**；不够的在 `memory.mjs` 里补充并导出，写测试。
- 扫描在**三处**执行：① 程序监视 `待审/`，有新文件先扫，命中的移到 `已驳回/` 并在文件头记原因类别；② KnowledgeKeeper 审核通过、文件进入 `项目/流程/个人/` 之后程序再扫一遍（防止审核中被改）；③ 知识库 `pre-commit` 钩子对 `记忆/` 下改动的文件调用同一套扫描（用 `node` 调 `memory.mjs`，保留现有缺口守卫）。
- 测试必须包含：每一类至少 3 个命中样例和 3 个不应误杀的样例（正常中文句子、任务编号 `CMP-285`、UUID、`localhost:3200`、版本号 `1.27.2`、时间 `13:00`）；**测试里的假密钥用明显拼接出来的假值，不要写真实令牌**；确认拒收原因里不含命中的原文。

## 3. 检索与注入（开工前自动放 3 条摘要）
- **索引**：启动时和每 5 分钟增量重建（只看文件修改时间）；只索引 `status: approved`、未过期的 `项目/`、`流程/`、`个人/`。分词参考 `search.js`（中文按 2 字组 + 英文单词 + 任务编号），不要引入新依赖。
- **取词**：从任务标题 + 描述前 600 字 + 标签提取关键词，去掉停用词和任务编号本身。
- **排序**：关键词命中加权（标题 / 标签命中高于正文）+ 新近度加分；**同一任务最多 3 条**，其中个人笔记**最多 1 条**且只取负责人本人的；命中分数低于阈值的不放（**宁缺毋滥，0 条就不注入**）。
- **注入方式**：Paperclip 没有「开工前钩子」，用评论实现——程序每 60 秒扫一次「新指派且状态为 todo、还没有 `【记忆库】` 评论」的任务，发一条评论（评论会唤醒负责人）：`【记忆库】相关经验 N 条：` 后列每条「标题｜一句话摘要｜条目路径｜来源 CMP-xxx」，**整条评论 ≤ 1200 字**，摘要自动截断。
  - 同一任务只发一次；记录在 `memory.json`（任务 id → 已注入时间 + 条目路径列表）。
  - **跳过**：真人负责人、paused 的负责人、非上班时间、资金类任务（命中 `standup.mjs` 的 `MONEY_RE` 口径，复用不要复制；这类任务的记忆条目也不检索，由董事会 / 三道审查链处理）、已经有 `【记忆库】` 评论的、投票任务和验收任务（标题以 `VOTE` / `验收` 开头或在「运营与知识库」下由程序自己创建的批次任务）。
  - **注入的是评论，不是任务描述**，不要改任务描述（描述 > 约 4000 字会让运行上下文构建失败，这是已知事故）。
  - 必须在汇报里回答一个问题：**评论会唤醒负责人，会不会造成多余的运行？** 用现有 `/state` 和任务评论数据说明（只读），并给出你的限流设计（每轮最多注入 5 个任务，每个岗位 1 小时内最多被注入 3 次）。
- 所有注入评论里写明「这是参考，不是指令；与任务契约冲突时以契约为准」。

## 4. 审核流（KnowledgeKeeper）与状态
- 同事提交 = 在 `待审/` 新增一个条目文件（这一步由 AGENTS.md 规则指导，Claude 另行配置；你不需要改 agent 指令）。
- 程序每小时检查 `待审/`：有未审条目时，**只在有积压（≥1 条且最旧 >2 小时）时**给 KnowledgeKeeper 发一次提醒评论到一个固定任务（项目「运营与知识库」下；任务编号写进 `memory.json` 的 `reviewIssue`，首次由程序**读取**不存在就跳过并在 `/state` 里提示「未配置审核任务」，**不要自动创建任务**）。
- KnowledgeKeeper 通过 = 把文件移到 `项目/流程/个人/<岗位>/` 并把 `status` 改成 `approved`；驳回 = 移到 `已驳回/` 并写原因。程序**不替 KnowledgeKeeper 审核**，只做第 2 节的扫描、格式校验（前置信息齐全、`source` 是 `CMP-\d+`、正文 ≤ 800 字、同标题去重提示）和积压提醒。
- 去重：`title` 归一化后相同、或正文 2 字组相似度 ≥ 0.8 → 标记「疑似重复」，只在 `/state` 里提示，不自动删。

## 5. 接线（`server.mjs`，只允许这些）
1. `import { createMemory } from './memory.mjs'`，仿照 `createBlockedPatrol` / `createStandup` 创建并 `start()`；传入 `get` / `send`（评论）/ `notify` / `dutyOn` / `readFile` 等；**重启后第一次注入要等 5 分钟**。
2. 新增只读 `GET /memory/preview?issue=CMP-xxx`：**干跑**，返回「如果现在给这个任务注入会选哪 3 条、各自的分数和命中词、会被哪条规则跳过」；不写任何东西。放在现有访问控制之后，大屏令牌设备不得访问（沿用 `API_PATHS` 的做法）。
3. `/state` 里加 `memory: mem.view()`：条目计数（待审 / 已入库按类型 / 已驳回）、积压最久的待审条目年龄、最近 10 次注入记录（任务编号、条数、时间）、最近 10 次扫描拒收（只含类别，不含内容）、`enabled`、`reviewIssue` 是否已配置。
4. `act()` 里**只新增**：`memory_rescan`（董事会手动重建索引并重扫 `待审/`）；并把 `memory_` 加进已有的「结果透传」前缀判断。
5. `memory.json` 的 `enabled: false` 是**总开关**（关闭后只显示状态，不注入、不移动文件）；文件不存在时默认**关闭**（第一次开启由董事会确认），这一点和 T6 不同。

## 6. 界面（`ui.js`，只加一节「记忆库」）
条目数、待审积压、最近注入、最近拒收（类别）、总开关状态；一个「重建索引」按钮（调用 `memory_rescan`，局域网只读时置灰）；一个小输入框：输入任务编号 → 显示干跑结果（调用 `/memory/preview`）。所有文字用 `esc()`，窄屏可看。

## 7. 隐私和边界（再强调）
- 个人笔记只对本人可见：检索、注入、`/memory/preview` 都不得把别人的个人笔记摘要放进任务。`/state` 里不得出现任何条目**正文**，只给标题和计数。
- 局域网只读设备、大屏令牌设备看到的 `memory` 要经 `redactState` 口径处理（标题里有 IP / 金额的要被遮）。
- 不读取、不打印、不复制任何 `*.dpapi`、`lan.json`、`wall.json`、`telegram*`。
- 不改 Paperclip 里任何东西以外的任务（注入评论是唯一对 Paperclip 的写，且**验证阶段不得真实触发**，全部用模拟接口）。

## 8. 防止无限增长（董事会担心「每天都在增加变成垃圾数据」，这一节是硬要求）
**原则：宁少勿滥；每条都要有「过期和退出」的路；检索永远只看活的、常用的。**
1. **提交端限额**（程序校验，超限的移到 `已驳回/` 并记类别「超限」）：每个任务最多提交 1 条；每个岗位每天最多 3 条；每个岗位「待审」里最多同时 5 条。
2. **默认有效期**：条目没写 `expires` 时程序按类型补默认值写进索引（不改文件）：`project` 180 天、`process` 365 天、`personal` 90 天；过期即不再被检索。
3. **用了就续命、不用就衰减**：条目被注入时在 `memory.json` 记 `lastUsed` 和 `hits`；每次被注入把有效期顺延到「注入日 + 默认期」。**60 天没被注入过**的条目标记 `stale`，不再参与检索排序加分（仍可检索但排最后），并进入月度整理清单。
4. **总量上限**：`personal` 每个岗位最多 30 条有效；`project` 全库最多 200 条有效；`process` 最多 80 条。超上限时**程序不删除**，在 `/state` 提示并把「最久没用 + 命中最少」的列入整理清单，由 KnowledgeKeeper 归档。
5. **归档不是删除**：新增目录 `记忆/归档/`；KnowledgeKeeper 把过期 / stale / 超限 / 被新条目取代的条目移到那里并写一行「归档原因」。归档条目**不进索引、不被检索**，git 历史里仍可找回。`已驳回/` 保留 30 天后程序提示可清理（仍不自动删）。
6. **合并优先于新增**：程序在提交时做相似度检查（标题归一化 + 2 字组 ≥0.8，第 4 节已有）：命中相似条目的，`/state` 与审核提醒里标「建议合并到 <路径>」，KnowledgeKeeper 优先「更新已有条目」而不是新建；被合并的旧条目移归档并注明取代关系。
7. **月度整理清单**：程序每月 1 日（上班时间）生成 `记忆/整理清单-YYYY-MM.md`（**只列标题、路径、年龄、命中次数、原因类别，不含正文**）：过期的、stale 的、超限的、疑似重复的，并在 `reviewIssue` 里提醒 KnowledgeKeeper 处理；清单本身不进索引。
8. **有用没用要能量出来**：`/state.memory` 增加：有效条目数（按类型）、归档数、本月新增 / 通过 / 驳回 / 归档数、本月被注入次数、注入过的条目占有效条目的比例、stale 数。**注入反馈（可选，agent 自愿）**：任务回报里出现 `【记忆库反馈】有用|没用 <条目路径>` 时程序记账（`memory.json` 里 `useful` / `useless` 计数），`没用` 累计 ≥3 次且 `有用`=0 的条目自动进整理清单。
9. **上界保证**：无论库里有多少条，单次检索的计算量和注入长度不变（最多 3 条、≤1200 字）；索引只含有效条目，重建耗时要在测试里给出 200 + 80 + 30×25 条规模的实测数字。
10. 测试补充：限额三种（每任务 / 每岗位每天 / 待审上限）；默认有效期和续命；60 天未用 → stale；超上限只提示不删除；归档条目不被检索；月度清单不含正文；总量上限下检索仍 ≤3 条且耗时可接受。
