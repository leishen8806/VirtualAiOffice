## 4. 动线与路径影响

检查脚本从 `office-layout.js` 导入真实的 `SEATS`、`FOYER_TARGETS`、`foyerTrip`、`plazaTrip`、`corridorPath`，并对 25 个岗位到 27 个既有目标的往返语义路线逐段采样。障碍采用仓库主体外框并加 0.3 m 人物余量。脚本也从 `cat-play.js` 读取公共点并对相邻公共点生成实际猫路线抽样。

- 人物：前厅路线在 `z≤12`，广场路线在 `x=-3.5` 或 `x=7`；仓库在 `z≥17, x≤-14`，不相交。
- 猫：当前可走地面不包含仓库用地，广场目的地仍在 `(2,23)`；不新增仓库公共点。
- T16 让路与看门狗：它们只处理既有路线上的会车；因为语义路线和可走地面均不扩展，不需要改让路规则。S2-2 只把仓库主体注册为静态碰撞，不能把 4 m 通道注册成障碍。
- v1 不实现“去仓库门口看看”、进仓库、装卸人员或访客路线。后续若开放，须先补门口排队点、室内路网、猫禁入和 T16 压力测试。

## 5. 零 token 环境动画

动画只在页面打开时运行，输入仅为固定种子 `dr-warehouse-v1` 与浏览器时间片；不读任务、订单、账本或网络，不写服务端。相同日期与 10 秒时间片产生相同状态。

| 动画 | 高档上限 | 中档 | 低档 | 实现与成本 |
|---|---:|---:|---:|---|
| 卡车进出 | 1 辆移动 + 1 辆静止 | 1 辆低频移动 | 2 辆静态 | 单个动态组，预设闭合轨迹；约 +1 call |
| 叉车往返 | 1 辆 | 1 辆，15 fps 更新 | 静态停靠 | 单个动态组，仓库内部短轨迹；约 +1 call |
| 货堆变化 | 3 组、每 30 s 切换可见层 | 2 组 | 固定一层 | 实例矩阵/可见性切换，不创造数量文本；约 +1 call |
| 月台灯 | 3 块发光材质 | 同左 | 关闭发光 | 只改材质发光色，不创建 `Light`；合并后约 +1 call |

固定种子只选择动画相位、泊位和预写动作，不生成营业额、订单数、库存数或“繁忙程度”。动态根节点必须 `userData.dynamic=true`，避免被 T10b 静态合并；低档静态替身不标 dynamic，可交给静态合并。

## 6. 外墙“商品供给”只读面板合同

**显示模型（不实现）：**

```js
{
  enabled: true,
  updatedAt: 'ISO-8601',
  index: 1.0,          // monetaryReport(...).cpi / priceIndex(...) 同口径
  supplyCapRatio: 0.0, // 0…1；经济引擎提供的供给量 ÷ 供给上限
  source: 'town',
}
```

空态：功能关闭、配置缺失、数据无效或读取失败时，只显示固定文字 **“经济系统未启用”**。面板不得回退到模拟值。`index` 显示两位小数，`supplyCapRatio` 显示百分比，不显示供应量、币值、真实库存或任何个人数据。刷新沿用办公室已有只读状态轮询，最多每 60 秒接受一次新签名；签名不变不重绘。

权限：局域网页面只读；大屏使用现有已鉴权状态，不在纹理、DOM、日志或 URL 中显示令牌；无按钮、输入框和写请求。不得增加 `buy / pay / purchase / wallet / balance / price` 命名的操作入口；显示字段统一称“指数”。数据源仅使用 `monetaryReport` 的 `cpi` 与未来 T20 明确暴露的供给上限，不能从账本自行推算第二套口径。

## 11. 风险、取舍与未决项

### 11.1 本次修订原因及已知事实 / 假设 / 推断 / 未知

- **修订原因：** 2026-10-20 董事会在 S2-0 评审后明确要求仓库主体不得小于 28×12 m。S2-0 的 28×11.5 m 方案少了 14㎡，因此恢复完整 336㎡，所有南侧设施整体后移，不再以接缝为由压缩仓库。
- **已知事实：** 当前广场、前厅、路线、环境随机生成位置与 T10b 合并规则已从代码读取；现有 112×88 铺装足以覆盖新园区；参考图只可作概念参考。
- **假设：** 28×12 m 的主体可用四列货架表达“云仓”，2.5 m 月台与 4 m 泊位在视觉上足够；面板未来能拿到供给上限。
- **推断：** 保留两条 4 m 通道并禁止人物入仓，可把 T16 风险控制在现有路线范围；静态合并与实例化可满足 calls 预算。
- **未知：** 实际相机下的屋顶遮挡、T20 最终字段、低端 GPU 的三档真实 calls/FPS。

### 11.2 最强反对理由（三项）

1. 该区域横向很长、主体高 7 m，可能遮住前厅、广场和西侧办公室的常用镜头；几何不冲突不等于视觉不冲突。
2. T20 尚未提供稳定的“供给上限”只读合同，面板可能长期只能显示空态；提前做动态面板收益有限。
3. 当前场景已偏重，动态卡车、叉车和面板即使满足 calls 数，也可能增加透明、阴影和 CPU 更新成本，低端设备风险仍在。

### 11.3 支持本方案的最强理由（三项）

1. 位置、叙事与广场形成清晰的“办公室/前厅—展销—云仓”关系，且不改任何既有人物路线。
2. 4 m 双通道、锁闭仓库和零 token 动画把碰撞、治理与运行成本限制在可逆的视觉层。
3. 施工可按常量、静态建筑、资产、动画、面板逐步验收；任何阶段失败都可停在前一阶段，不需要大爆炸式改造。

### 11.4 结论与最小验证实验

**Verdict：** 推荐采用修订后的完整 336㎡ 坐标方案，但只批准 S2-1 常量/测试；建筑施工要等视觉体块实验通过。置信度 **82%**。面积、铺装与树木冲突现已可复现，决定结果最敏感的变量仍是屋顶遮挡、低端渲染开销和 T20 数据合同。

- **Hypothesis：** `x=-42…-14, z=17…29, 高 7 m` 的半透明灰盒不会阻断广场、前厅、Logo 与主要办公室的常用视线。
- **Test：** S2-1 后单独生成无材质细节的灰盒截图，验证桌面默认、DR 广场、仓库、大屏巡游、390px 五个机位；不接动画和数据。
- **Success Metric：** 五个机位都能看清目标区域，Logo/入口不被遮，calls 增量 ≤2。
- **Failure Threshold：** 任一常用机位核心目标被遮超过约 25%，或需移动既有广场/前厅才能看清。
- **Time Limit：** 半天。
- **Decision After Test：** 通过才做 S2-2；失败则优先把檐口降到 4.5 m、屋脊降到 6 m或将主体西移 2 m，再重跑几何与截图，不直接进入精模。

### 11.5 推荐项与最不确定三处

- 参考图借鉴：W1/W2/W3 的业务分区、客户/货物/平台三类动线概念、主入口与物流入口分离。
- 不借鉴：图中真实馆号、数量、面积、租户、道路比例和地址；本方案也不画三条彩色地面线。人物不入仓时，地面线会暗示不存在的可走/运营路径。若 S2 后续开放人物路线，再独立评估。
- 仓库入口：v1 保留锁闭的视觉人行门，不为人物开放；这是风险最低的做法。

最不确定三处：
1. 完整 12 m 深主体和南移泊位在现有相机、390px 视口中的遮挡程度。
2. 施工时扩展棕榈移除条件后，浏览器实测能否证明后续所有环境对象像素级不漂移（规划脚本只证明 RNG 消费顺序）。
3. T20 能否提供稳定、无敏感字段的 `supplyCapRatio`，以及 T10b 低端 GPU 的真实帧时间。

## 12. 可复现检查

正常检查：

```powershell
node docs/dr-warehouse-checks.mjs
```

故意把主体缩成 28×11.5 m，必须非零退出：

```powershell
$env:DR_WAREHOUSE_CHECK_MUTATE='shallow'
node docs/dr-warehouse-checks.mjs
Remove-Item Env:DR_WAREHOUSE_CHECK_MUTATE
```

故意把第一列货架移入 DR 广场，也必须非零退出：

```powershell
$env:DR_WAREHOUSE_CHECK_MUTATE='overlap'
node docs/dr-warehouse-checks.mjs
Remove-Item Env:DR_WAREHOUSE_CHECK_MUTATE
```

脚本直接导入当前 `office-layout.js` 和 `cat-play.js`，现有坐标变化会让规划检查跟着变化，不复制现状常量。
