### 指标与可信度

- 作息只读 `../workhours/workhours.json`：目前金边每天08:30–17:30，周日也上班。窗口为最近14/7个**已结束**的上班日，今天未结束的观察不参与增减判断。
- 出勤：上班时间实际观察到idle/running的一天。paused/error/terminated另记不可用天；同一天可同时有可用与不可用观察。没有观察不是缺勤，不可用不算空闲。历史账本不能还原出勤。
- 有产出日：成功运行或完成任务。运行、完成、评论沿用stats；新增数据字段不改变旧计数。成功率=成功/(成功+失败+超时)，取消单列且不算失败、也不进成功率分母；失败判定直接复用T4导出的isFailure。
- 忙碌：真实startedAt/finishedAt与当天上班时段交集的并集；跨午夜按各日裁剪，并发不重复。缺真实时间戳为未知。利用率=忙碌/该日作息时长（当前9小时）；页面汇总显示日利用率中位数。不可用或无出勤观察的日期不给利用率。
- 队列：08:30、17:00所在分钟实采todo/in_progress/in_review/blocked及总数，不补错过的时点、不倒推历史。完整积累天数要求当日两份快照齐全；不足7天，涉及队列的扩编/缩编规则不触发。队列列显示最后一次下班快照总数。
- 等待：有明确todo时间/活动事件且运行明确关联任务时，todo→第一次运行的中位数。不拿createdAt或updatedAt冒充todo迁移时间，不用岗位运行代替任务运行；没有则未知。
- 返工：带“【第 N 轮退回】”的评论条数，按任务+评论ID去重，不把普通评论或自检失败算返工。每轮最多读取20个更新过任务的评论，积压时明确提示扫描不完整。历史归属只有当前负责人，不能还原改派前的负责人。
- 阻塞占比：窗口内所有队列快照blocked总和/已派发总和；这是快照占比，不是任务历史时长占比。
- 有效观察日：该岗位当天有实际状态观察，或账本有运行/完成/评论。≥14“可用”，7–13“参考”，<7“不足以判断”。足够运行记录不代表历史出勤已知，各指标仍各自显示缺口。2026-10-29之前不可达到“可用”；目前账本只有5个日历日，不能得出任何增减结论。

### 建议规则与安全边界

`workload.json.thresholds`可调，未知/非法阈值回退默认；页面展开显示实际使用值：

```json
{"busyUtilization":0.7,"busyDayShare":0.6,"queueTodo":3,"queueDayShare":0.5,"waitMs":14400000,"successRate":0.7,"productiveDayShare":0.2,"lowUtilization":0.05,"failureRate":0.3,"blockedShare":0.5,"reworks":3,"unavailableDayShare":0.5}
```

- 扩编：至少7个观察日、至少7个完整快照日；日利用率≥70%的比例≥60%，下班todo≥3的比例≥50%或真实等待>4小时，成功率≥70%。忙碌日利用率有缺口时不出扩编。失败/阻塞/返工问题先排查，不扩编。
- 缩编/合并：至少14个观察日，产出日≤20%，日利用率中位数≤5%，14日利用率全部已知，本人与同类岗位同窗口每个上下午快照全部为0，有当前idle/running的同职能同项目承接岗位。缺快照、缺同类、同项目不明确或候选当前不可用均不触发。
- 同职能仅按岗位title去除等级与数字后的精确匹配，同项目按当前已派任务projectId交集确认；不猜替代关系。该规则保守，可能漏掉实际可以承接的岗位。
- 排查：失败率≥30%、快照阻塞≥50%、返工≥3条，或观察≥7天且不可用天≥50%。可在低可信度时提示排查，但不提示增减。每条建议附窗口、实测、阈值、数据缺口和承接候选。
- GoSenior/DBEngineer/LedgerAuditor/SecurityReviewer及名称/title含账务、账本、资金、支付、提现、ledger的岗位不出缩编，扩编标“需董事会审批”。不会更改任何岗位或资金审查链。

1. 点「打开 BotFather」→ `/newbot` → 起显示名 → 起用户名（以 `bot` 结尾）→ 拿到令牌。
2. 把令牌粘贴进页面、点「验证并接入」：服务器调用 `getMe` 验证，自动设置 bot 的名称、简介、命令菜单，清掉残留的 webhook。
3. 点「生成订阅链接」→ 在手机或装了 Telegram 的设备上打开链接、点 Start：一次性、15 分钟有效，用一次就失效；只有拿到链接的人才能订阅。
4. 「发测试消息」确认；之后可以随时停用 / 启用、移除订阅人、解除接入。

三个用途，一个 bot 只能有一个用途：
- **办公室通知**：待审批、待回答、待验收、运行出错，下班那一刻发每日战报。
- **Paperclip 通知**：任务完成、派发、董事会决定。
- **客服（将来）**：只接入并配好名字，**不收也不回任何客户消息**；等客服角色和已审核（public + verified）的问答准备好再启用。

通知是**只读**的：Telegram 里只有 `/start`（绑定）、`/status`（现在有几件事等你）、`/stop`（取消订阅），不能批准或回答，处理请回办公室页面。没绑定的人发什么都不回应；只处理私聊。用 `getUpdates` 长轮询，不需要公网地址。

**令牌怎么保存**：只有董事会在页面里粘贴，Claude 和 agent 看不到。办公室 / Paperclip 通知 bot 的令牌用 Windows DPAPI（只有当前 Windows 账户能解开）加密存在本目录 `telegram-*.dpapi`，明文只在服务器内存里，不写日志、不回显错误里的令牌、不进 Git；客服 bot 的令牌只存进 Paperclip 密钥库（`telegram/<用户名>`），以后绑定给客服 agent，本进程不留。订阅人和已发通知的记录在 `telegram.json`（不含令牌）。

## 人员绑定与快捷操作（2026-10-17 董事会选定）

「📨 Telegram」里的「人员」区：苏晨（董事会）+ 自定义人员名册（名字、角色，可随时加人 / 删人；董事会成员不能删）。

**绑定到具体的人**：给某个人在某个 bot 上点「生成绑定链接」（15 分钟、用一次）→ 把链接发给他本人 → 他在手机上打开并点 Start → 页面最上面弹出「有人申请绑定：昵称 (@用户名) → 苏晨」→ 你确认是本人再点「确认」才生效；链接转发错了也不会绑错。一个人在一个 bot 上只绑一个账号（重新绑定会换掉旧的）；之前没归属的老订阅可以用下拉框直接指定给某人。

**按人分发通知**：每人单独选要收哪几类（待审批、待回答、待验收、回答没送到、运行出错、每日战报、任务完成、任务派发、董事会决定；任务派发默认不推，太吵）；每人可设**静音时段**（金边时间，例如 22:00–07:00），静音期间不推、结束时补一条「现在的情况」汇总。

**快捷操作（每人单独开关，默认关，只有董事会成员能开，开的时候要点两次确认）**：开了之后，这个人在 Telegram 里收到的通知会带按钮——
- 「已读」：收起按钮；
- 「叫醒它继续」（回答没送到）：在任务里发一条评论叫醒负责人；
- 「验收通过…」（待验收）：**要二次确认**；验收前服务器会再核对一遍——**资金类任务、还在 agent 审查链里的任务、已经不在待验收的任务，一律拒绝并让你回电脑**。
审批、回答问题、取消任务、资金类任务**一律不能经 Telegram**。
安全措施：按钮里只放一次性随机串，动作存在服务器内存里；30 分钟过期、用一次就作废；核对点击者就是绑定的那个账号且仍是董事会成员且仍开着快捷操作；每次操作（包括被拒绝的）写入本目录 `telegram-audit.log`，验收 / 叫醒会在 Paperclip 评论里注明「（苏晨，经 Telegram）」。风险：手机丢失或 Telegram 账号被盗时，别人也能做这三件事；觉得不放心就关掉快捷操作。

**接管已有 bot 的提醒**：向导接入一个 bot 时会改它的名字、简介和命令菜单；如果这个 bot 设了 webhook（说明别的服务在用它），默认拒绝，必须勾选「我确认接管」才会清掉 webhook——否则那个服务会收不到消息。

**这是我没有用真实 bot 验证过的部分**：令牌格式校验、Telegram 拒绝假令牌、错误里不回显令牌、向导页面渲染都测过；真正的 `getMe` → 设置 → 订阅 → 发消息这一整条，需要你用一个真实令牌走一遍，第一次请留意页面提示和服务器终端里的 `[telegram]` 日志。

## ⚖️ 内容审批委员会（committee.mjs，董事会 2026-10-17 设立）

左下「⚖️ 委员会」。章程在知识库 `委员会/章程.md`。5 位现有岗位的同事投票决定「对外内容」能不能用（客服问答、对外文章、三语文案、通知模板）；**通过 = 知识库里标为已审核，发布 / 部署仍走原审批**。

- **委员（5 票）**：Lead（Helix，整体把关）、PM（说得对不对）、Architect（Arc，架构与边界）、Backend2（B2，技术准确性）、Frontend2（F2，展示与可用性）；作者回避时由后备 Reviewer2 顶上。各人在晨会、内容审批、超时验收里的评审角度分别写在 `committee.mjs` 的 `MEMBERS` 里（`angle/ask`、`standup`、`accept`），是名单和角度的唯一来源。
- **规则**：每项 5 票里 ≥3 票通过且没人「升级」→ 通过；任何一票「升级」→ 转给你；否则「要修改」退回作者（附各委员意见，自动建修改任务）。缺票按未通过算。
- **红线内容**（价格定价、法律条款与隐私政策、赔付退款承诺、资金账务的对外说明、个人信息）：委员会先投票，**你最后确认**才生效；确认请求出现在「等你处理」里，附委员会的建议和各人的投票理由。文章头部可写 `redline: price|legal|promise|money|pii`；没写但文中出现相关字眼，程序会自动按红线处理（宁可多问你）。
- **怎么提交**：文章头部写 `submit: committee` 且 `status: draft`（可选 `author:`、`redline:`）。工作日（金边时间）**11:00** 自动开一批（有待审内容才开，没有就不花额度），**16:00** 统计（5 票到齐提前统计）。页面里的「现在就开票」可以不等 11:00。
- **固定逻辑用程序做，投票用 agent 做**：开票、分发、统计、改文章状态（只改头部一个字段并在知识库提交）都是程序，不花额度也不会被 agent 误判；5 位委员各收到一个独立的投票任务（互相看不到），在任务里发 `VOTE 序号: APPROVE|CHANGES|ESCALATE | 理由`，格式不对按缺票算。
- **你随时可以撤销**任何一项已通过的决议（页面里「撤销审核」，改回草稿）。开票、统计结果会推到 Telegram（办公室通知 bot 的「委员会决议」类别）。
- 状态记在 `committee.json`；投票任务和修改任务都在项目「运营与知识库」里。

## 审核绑定版本（T15，2026-10-20；默认关闭，重启后生效）

验收证据块的首行是 `【验收证据】对象版本：<Git 提交号 | 无 Git：逐个文件写 SHA-256>`，之前没有任何程序核对“同事验证完又改了东西”的情况。本任务让程序**在验收的那一刻**把证据里的版本和**当前实际版本**做只读核对，把结果摆在验收人面前，并挡住「版本已变」的任务被自动验收。**只做只读核对，不替任何人做决定，也不向 Paperclip 发任何写请求。**

- **机器可读写法**（`evidence-version.mjs`）：`【验收证据】对象版本：` 之后分号分隔 `git:<仓库绝对路径>@<提交号>`（7–40 位十六进制）与 `sha256:<文件绝对路径>=<64 位十六进制>`；全角 / 半角冒号、分号、等号容忍，Windows 反斜杠 / 正斜杠都处理。旧写法一律「无法核对」，不报错。
- **核对语义**：git 条目取仓库当前 HEAD（`git -C <repo> rev-parse HEAD`，`execFile` 不经过 shell、5 秒超时），以证据提交号为前缀一致 → `一致`；不一致再用 `rev-list --count` 与 `diff --name-only`（只取文件名，最多 20 个）给出「之后新增 N 个提交、改了哪些文件」；证据提交不在当前历史 → 写明；`status --porcelain` 非空 → 另标「工作区有未提交改动（N 项）」，只给数量。sha256 条目重算哈希比较：`一致 / 已变 / 缺失 / 无法核对（文件过大）`。汇总：全一致 = `版本一致`；任一已变 / 缺失 = `版本已变`；证据缺版本 / 写法不可解析 = `证据缺版本（无法核对）`；其余 = `无法核对（原因）`。
- **安全边界（硬规则）**：路径必须落在白名单 `roots` 内（`realpathSync.native` 规范化后，防 `..` / 符号链接 / 盘符大小写），否则 `无法核对（路径不在允许范围）`；受保护文件（`lan.json`、`wall.json`、`telegram*`、`*.dpapi`、`.env*`、`*ed25519*`、`*.pem`、`*.key`、`config.json`）一律不读不求哈希，命中即 `无法核对（受保护文件）` 且不把路径写进日志；提交号只许十六进制，含空格 / `;` 一律不认；单文件哈希上限 50 MB；一次核对最多 10 个条目；输出一律走 `redactText` 脱敏，不输出文件内容。结果按「任务更新时间 + 证据评论 id」缓存，git HEAD 每次现取、缓存不超过 60 秒。
- **界面**（`ui.js`）：董事会「待验收」卡片上对每个任务显示核对结果徽标（绿「版本一致」/ 红「版本已变（N 提交 / M 文件）」/ 灰「证据缺版本 / 无法核对」），悬停显示明细（文件名最多 20 个）；版本已变时点「验收通过」会多一次确认「证据对应的版本已经变了，确定仍要通过吗？」——二选一、默认焦点在「取消」、**不禁用按钮**，最终决定权在董事会；治理中心新增「版本核对」折叠区（编号、标题、结果、证据评论时间）。页面按需拉一次 `/evidence-version`（服务端缓存 60 秒），不在每次轮询里跑 git。
- **挡住超时验收**（`acceptance.mjs`，只加两处过滤，`≤15 行`）：批次组装时核对为 `版本已变` 的任务**不进入委员会投票**（等同交董事会，批次记录写明「版本已变」）；`证据缺版本 / 无法核对` 的可以进入投票但标记 `version:false`，且所有投票任务规则最前面加「本项版本未能核对，不得仅凭自述给通过」，最坏情况提示语仍 ≤3600 字（沿用既有测试）；核对接口失败按 `无法核对` 处理，**不得卡死验收**。
- **接线**（`server.mjs`）：新增只读 `GET /evidence-version?issue=CMP-xxx`（单个）与 `GET /evidence-version`（批量，最多 20 个，取当前「待验收」），放在访问控制之后，大屏令牌设备经 `API_PATHS` 直接 403；`/state` 不加字段；无 `act()` 改动。
- **总开关**：`evidence-version.json` 的 `enabled:false` 为总开关，**默认关闭**（缺省 / 损坏也按关闭）；关闭时接口返回 `{disabled:true}`、页面不显示徽标、超时验收过滤不生效。`roots` 在这里配置，由董事会调整。

## 完成策略（completion-policy.mjs，DS-7 R1，2026-10-23；默认关闭，重启后生效）

把任务写成 `done` 的三处入口统一过一道「完成策略」：**本机董事会点「验收通过」**（`server.mjs` 的 `act()`）、**Telegram 验收**（`tgActions.review`）、**超时验收委员会批次**（`acceptance.mjs`）。判定复用既有 `done-rules.mjs` / `command-view-validate.mjs`，不另造规则；**默认 `off`，行为与改前完全一致**。

- **三种模式**（`completion-policy.json`，运行数据、**不入库**；仓库只提供 `completion-policy.json.example`，内容 `{ "mode": "off" }`）：
  - `off`：一律放行，不读证据（默认；缺文件 / 坏文件 / 未知字段 / 非法值都按 `off`，失败关闭）。
  - `warn`：一律放行，但把证据问题写进 `reasons` / `audit`，并在验收评论里附一行「完成策略（warn）提示」。
  - `enforce`：证据无效时**拒绝完成**——不发 `PATCH status:done`；`review` 返回中文错误并列原因码，自动验收批次跳过该项、记 `POLICY_BLOCKED`、不影响其它项。
- **判定口径**：证据缺失 → `NO_EVIDENCE`；版本不一致 / 无法核对 → `VERSION_MISMATCH`；受保护测试不符 → `PROTECTED_TEST_MISMATCH`；执行者自评 → `REVIEW_NOT_INDEPENDENT`；验收者不在 `boardActors` → `BOARD_ACCEPTANCE_REQUIRED`；任务创建早于 `enforcedSince` → `LEGACY_BASELINE`（按旧任务放行）。原因码只来自 `REASON_CODES` 与本模块新增并导出的 `NO_EVIDENCE`、`OVERRIDE_NOT_ALLOWED`。
- **人工特批**：仅 `enforce` 下、仅**本机完整权限**（`localFullAccess`，局域网 / 大屏恒为 false）、理由去空白后 **≥10 字**时放行，并在 `audit` 记 `override:true`、理由、时间；LAN / 大屏永远不能特批（尝试会得到 `OVERRIDE_NOT_ALLOWED`）。特批不掩盖原问题，`reasons` 仍保留。
- **开关读取**：启动时读一次 `completion-policy.json`（与其它默认关闭开关一致）；`warn` / `enforce` 要求合法 ISO `enforcedSince` 与字符串数组 `boardActors`，否则回退 `off`。
- **覆盖范围**（与 `done-rules.mjs` 的 `enforcementBoundary` 同口径）：覆盖的是「办公室 3D 的任务验收流程 / 完成判定调用」；**未覆盖**：Agent 绕过办公室 3D 直接改 Paperclip 完成状态、Paperclip 原生领取 / 执行锁和其它入口、未接入本规则引擎的历史或外部工作流——这些必须单独授权和验证。
- **安全边界不变**：局域网访问码、只读、Host 校验、`act()` 鉴权段保持原样；特批复用现有「本机完整权限」判定，不新增身份机制；不联网、不装依赖。自检：`node --test tests/completion-policy.test.mjs tests/completion-policy-wiring.test.mjs`。

## T12 协作关系图（2026-10-19；只读，数据来自事件账本）

### 数据来源与「协作」的定义

## T13-rework-cap：有边界的返工（识别返工轮次，超限转人工，挡自动流程）

【依据】知识库《任务管理流程》第 6 节：返工留在原任务里，问题编号 R1、R2 在整个任务里不变，同一任务退回到第 3 轮就停下、升级给 Lead 和董事会。本任务让程序**识别**这条规则并**提示**，但不替人做决定。

### 语义与识别（`rework.mjs`）

只有「提交验收之后被评审员 / 委员 / 董事会退回」或执行者提交「第 N 轮修复」的事件才计入轮次；提交前自检不算。轮次取退回评论与修复评论的最大轮次，`roundsSource` 标明来源（`return` / `fix` / `both`）。模板三类评论：

- 评审退回：「【第 N 轮退回】」+ 若干 `R<n> ｜ 对应 AC-x ｜ 问题：… ｜ 复现 / 证据：…`；
- 执行修复：「【第 N 轮修复】对象版本：…」+ 若干 `R<n> ｜ 修复：… ｜ 复验：… ｜ 状态：已修 / 未修（原因）」`；
- 评审复核：「【第 N 轮复验】R1 通过 / 未通过 ｜ …」。

标题行容忍全角 / 半角括号、「第 2 轮」「第二轮」与前后空白；修复标题在轮次后还可带括注（如「董事会例外已批准」）。**无法解析的格式不猜测**，记为「格式不全」并给出原因（缺「对应 AC」/「复现 / 证据」、修复缺 R 项 / 修复缺状态、R 编号重排 / 复用等）。只看 agent 评审员和董事会写的评论；程序自己的评论（标记 `【返工巡检】`）不参与计数。每任务输出：`rounds`（退回与修复评论的最大轮次）、`roundsSource`（`return` / `fix` / `both`）、各 R 项状态（`open` 未修 / `fixed` 已修待复验 / `verified` 复验通过 / `failed` 复验未通过）、`openItems`、`repeatedItems`（同一 R 项在 ≥2 个轮次的复验里都未通过）、`formatIssues`、`ignoredMentions`（排除的「提到 / 引用」条数）、`capped`（`rounds ≥ 3` 且任务尚未结束）。


修复评论即使没有对应的退回评论也会建立 R 项：显式「状态：已修 / 未修」优先；没有状态时「已修正 / 已修复 / 已修」按 `fixed`，含「未修」按 `open`，否则按 `open` 并记录「修复缺状态」。修复标题没有 R 项仍计入轮次但记录「修复缺 R 项」。巡检提示使用「已进行到第 N 轮返工」并标明依据；复验标题不参与轮次。

识别规则：**只认「评论里真正的标题行」**——标题必须单独出现在某一行的行首（允许行首空白及 ≤6 字符 Markdown 前缀：`#`、`>`、`*`、`**`、`-`、数字序号等），且被 `【…】` 或 `[…]` 括起（全角 / 半角括号都认）；正文中间「提到 / 引用」别的任务的「第 N 轮退回 / 修复 / 复验」字样一律不算，只计入 `ignoredMentions`（只给数量）。一条评论可有多个标题行，各自处理；同一条评论里的 R 项只归属于它上面最近的一个标题行。退回标题行之后必须能解析出至少一个 `R<数字> ｜ …` 条目，否则记为「格式不全：退回缺 R 项」放进 `formatIssues` 且不计入轮次（防引用模板误报）。

### 阈值与动作（`rework.json`，默认如下，可调，页面显示用哪些阈值）

`capRound: 3`（达到第 3 轮即超限）、`warnRound: 2`（第 2 轮提示「再退一轮将超限」）、`repeatItemRounds: 2`、`maxPerScan: 6`。**总开关 `enabled: false` 默认关闭**；文件不存在 / 损坏（`corrupt` 提示）均按关闭处理，不崩溃、不覆盖损坏文件、重启保留已发记录。所有动作只在**超限**这一种情况发生：

- 超限：对同一任务**只做一次** ① 发一条评论（首行 `【返工巡检】`）：已退回到第 N 轮、未关闭 R 项清单（编号 + 一句话，不贴证据原文）、「按流程请 Lead 与董事会决定：继续 / 拆分 / 换人 / 取消；在决定前请不要再自行提交验收」；② 通知董事会一次（沿用现有 `notify`）。同一任务以后不再重复发（也保证同一任务 24 小时内最多一条巡检评论）。
- 资金类任务（复用 `standup.mjs` 的 `MONEY_RE` 口径，不复制）：同样识别与显示，但**不自动发评论**，只通知董事会一次。
- 预警（第 2 轮）与同项重复未通过、格式不全：只在治理中心显示，不发评论、不通知。
- 每轮扫描最多 6 个任务；重启后第一次扫描等 5 分钟；每 30 分钟扫一次状态为 `in_progress / in_review / todo / blocked` 且评论里出现过「退回」的任务（评论按任务更新时间缓存，只读 GET）。**不改状态、不改负责人、不取消、不拆分、不替任何人做决定。**

## T16-pedestrian-deadlock：行人窄通道解死锁

`pedestrian-traffic.js` 记录阻挡者，`director.js` 对连续 1.5 秒无位移且确有行人阻挡的行动做确定性让路：离开优先、事件时间更早优先、同刻按 agent id 排序；低优先级退到有碰撞校验的局部安全点，最多 3 次，每次最多等待 6 秒。让路继续使用人物净距和家具碰撞检查，不新增动作阶段，显示为已有 `queued`。达到上限后放弃本次互访并沿合法路径回到工位。

每个行动阶段有 45 秒看门狗；阶段持续无完成时回到 home 并记录 `[director] 行动超时，已复位`，带人物名、阶段、坐标和目标。正常行走时每次有实际位移都会重置阶段计时，因此最长约 60 米路径按 1.4 米/秒约 42.9 秒，仍留有约 2 秒余量；连续堵塞不会永久占住队列。

T16 测试覆盖窄通道面对面、三人门口净距、20 次确定性重复和看门狗复位。浏览器压力脚本的 30 轮实测需在上班时间由维护者手动执行；本次未启动第二个服务。

### T16c 压力修复

T16b 固定种子测试发现，让路者被第三人挡住时会保持同一等待环，放弃行动又会直接跨墙复位。T16c 将所有正常放弃改为沿已走合法路径返回，只有 45 秒看门狗保留一次不可见过程帧的最终复位；让路链按同一个确定性最高优先级传播，退路再次被通行者堵住时交换通行方，并为同一对象增加 2 秒冷却。办公室内部路线直接接门口通道，不再统一绕到房间最右侧后折返；家具碰撞仍会为真实桌椅生成局部绕行。

压力测试使用 200 个固定种子、每种 12 个事件、每种最多 2500 步，并单列 53、81、91、161 四个回归用例。休息区和会议室使用不同座位，避免把两个真人安排在同一张椅子的不可完成输入误判为行人死锁；四个历史种子另以原始座位选择重放。测试缓存墙段、只跟踪会动的 12 人，并以轻量第二遍验证确定性，覆盖不变且耗时低于 30 秒。

## M5-2 账号与会话原语

`M5-2` 在 `multitenant.json` 里新增子开关 `auth.enabled`，只有 `enabled === true` 且 `auth.enabled === true` 时认证路由才生效；任一缺失、损坏或不是布尔 `true` 都按关闭处理。当前只实现认证原语，不开放任何公司业务数据读取，也不改变既有 `/state`、`/kb`、`/issue`、`/foyer`、`/act` 或首页的访问边界。

新增路由只有 5 个：`POST /auth/login`、`GET /c/:slug/auth/session`、`POST /c/:slug/auth/logout`、`POST /c/:slug/auth/change-password`、`GET /c/:slug/whoami`。需要会话 cookie 的三个接口放在 `/c/:slug/auth/…` 之下，是因为 cookie 的 `Path=/c/<slug>/` 按 RFC 6265 只会发给该前缀之下的请求；放在旧的 `/auth/*` 路径下浏览器根本不会带 cookie（M5-2b 缺陷 1 方案 A）。这些路径可以绕过局域网共享访问码登录页，但范围严格只限这 5 个精确模式，其余 `/c/…` 路径一律不放行；老板会话不会自动放行其它旧接口。大屏令牌设备访问这些新路由仍然是 403。

账号文件存放在 `multitenant/tenants/<companyId>/auth/accounts.json`，会话文件存放在 `multitenant/tenants/<companyId>/auth/sessions.json`，都使用原子写入。口令用 `scrypt`（`N=32768,r=8,p=1,keyLen=32,maxmem=64MiB`）哈希，只保存盐和哈希，不保存明文；会话只保存 `SHA-256(sid)` 和 `csrfHash`。cookie 名为 `vao_sid_<slug>`，属性为 `HttpOnly; SameSite=Strict; Path=/c/<slug>/; Max-Age=604800`，不设置 `Domain`，当前局域网 HTTP 试点不加 `Secure`。

平台管理员仍然是运行服务的这台电脑，不提供网页上的账号创建入口。创建 / 重置 / 禁用 / 启用 / 列出账号要用本机命令：

```bash
node tools/tenancy-admin.mjs create-account --company <slug> --username <u> --role <company_owner|company_member|company_viewer>
node tools/tenancy-admin.mjs reset-password --company <slug> --username <u>
node tools/tenancy-admin.mjs disable --company <slug> --username <u>
node tools/tenancy-admin.mjs enable --company <slug> --username <u>
node tools/tenancy-admin.mjs unlock --company <slug> --username <u>
node tools/tenancy-admin.mjs list --company <slug>
```

初始口令和重置口令只在命令输出里显示一次，不写入文件、日志或审计。首次登录若 `mustChangePassword === true`，该会话只能访问 `session / change-password / logout`，访问 `whoami` 会收到 `403 需先修改口令`。

登录与改口令的旧口令校验共用同一个**按账号**限速器：15 分钟内 5 次失败后该账号被锁（指数退避，最高 15 分钟）。这是安全与可用性的设计取舍，缺点是**合法用户也会被别人的爆破连坐**：只要有人对该账号连续失败，正确口令在其后一段时间里同样会收到 429。缓解办法是董事会本机执行 `node tools/tenancy-admin.mjs unlock --company <slug> --username <u>` 立即清除该账号的失败计数与锁定期（会写一条 `account_unlocked` 审计）。

CSRF token 由「每安装一份的随机密钥 + `sidHash` + 代数」派生（`multitenant/auth-secret.key`，权限失败时在 `/platform/tenancy` 报警），服务端只存摘要；`session` 接口重复返回同一个当前有效 token，只在登录成功与改口令成功时轮换，多标签页不会互相作废。来源 IP 的限速摘要同样用这把每安装密钥做 HMAC，不能从「数据目录 + 月份」推算。

### 调度建议视图（L3b）

`scheduler-view.json` 默认关闭。开启后，`GET /scheduler/suggest` 复用同一次 `/state` 聚合得到的任务、同事和审批快照，运行 `scheduler-core` 的确定性校验，只返回任务编号、排名和原因码，不领取、不派发、不改状态、不写 Paperclip。数据过期返回 `STALE_DATA`；预算未知保留为 `BUDGET_UNKNOWN`；每次计算只在内存环形缓冲保留最多 100 条无正文 `decisionRecord`。治理中心按需显示前三项建议及被跳过原因码，并明确标注“仅供董事会参考，系统不会自动领取或派发”；页面轮询和隐藏页面不刷新该视图。

可靠读取到的依赖为 `done` 或 `cancelled` 时均视为满足；取消依赖不会继续阻塞下游，但取消本身不等于成功交付。依赖字段缺失或无法可靠读取时由 L3c 的 `DEP_UNKNOWN` 阻断。`in_review` 不可领取，只有 `todo` / `backlog` 且已分配负责人时才可能进入候选，避免把审核中的任务重新派发。预算未知只产生警告，不当作零预算或充足预算。

### 调度建议真实字段（L3c）

L3c 将调度视图的输入接到真实 issue 字段，但只在 `scheduler-view.json` 开启时补取：`priority`、`createdAt`、`assigneeAgentId`、父任务字段和完整 issue detail 的 `blockedBy`。原始 issue detail 的可靠依赖形状是 `blockedBy: array`，依赖项只保留 `id / issueId / identifier / status`；若 detail 没有 `blockedBy` 字段或补取失败，内部任务标记 `dependencyKnown:false`，`scheduler-core` 以 `DEP_UNKNOWN` 阻断建议，不默认认为没有依赖。`issue.blockers_updated` activity 事件只证明阻塞集合发生变化，不含可靠的当前依赖状态，因此不作为无阻塞证据。

未分配的 `todo / backlog` 任务进入独立的“待分配”建议：同项目近期完成记录优先，其次当前并行数少者，排除暂停、报错、终止和预算耗尽；资金类任务不提供建议负责人。输出只含任务编号、最多三个 agent id 和原因码，不含标题、描述或评论正文。规则版本为 `L3a-3`，系统不会自动分配。

## H2：state 最近成功快照与健康后台刷新

`state-last-good.mjs` 提供单次并发聚合、凭据字段递归剥离、内存快照和 `state-last-good.json.tmp` + rename 原子持久化。启动读取合法成功快照，缺失/损坏则忽略；磁盘写失败保留内存，不覆盖上次成功文件。JSON和临时文件不在静态白名单。快照包含原 `at`，不包含操作令牌、访问码、密码、密钥、Cookie或授权字段；非枚举调度来源不持久化。

`state()` 的 agents/dashboard/issues 为必需来源；runs/approvals/activity/approvalsAll/backlog 可选失败置空，并返回 `gaps: [{source, reason:'UPSTREAM_UNAVAILABLE'}]`。依赖缺失运行、活动、backlog的今日统计使用 `{value:null,reason:'UPSTREAM_UNAVAILABLE'}`，不把未取得数据当成已知零。正常聚合字段保持，健康冷缓存例外按真实未知报告；活动缺失不补造会议/事件/奖项，审批全集缺失不生成审批动画事件。

必需来源失败时 `/state` 返回200的最近成功副本，`actToken:''`，附 `stale:{active:true,since:<原at>,ageMs,reason:'UPSTREAM_UNAVAILABLE'}`；快照超过30分钟改为 `STALE_DATA`，仍200。没有可用快照返回503：`{error:'STATE_UNAVAILABLE_NO_SNAPSHOT',reason:'UPSTREAM_UNAVAILABLE'}`。成功恢复不带stale；降级/恢复各只在状态转换时打印一条日志。LAN/大屏仍通过原脱敏出口，快照不因读请求被修改；`/act` 鉴权与上游失败行为完全不变，不使用快照假报写入成功。

`healthReport()` 永远返回缓存并按需启动单个后台刷新，刷新间隔30秒、超时20秒，失败保留原报告并附stale；首次未加载返回warn/“健康数据暂不可用”及NOT_LOADED，不虚构健康。仍拉 `heartbeat-runs?limit=1000`，复用H1 `buildHealth`，不降低limit或改变判定。`get`仅允许此后台刷新传入AbortSignal，其余调用继续8秒超时。

验证用注入假上游和提取的实际state/路由，不加载真实server、不重启服务、不写Paperclip。H2交付后由董事会手动重启并验正常、慢上游、首次无快照及重启文件恢复；顶部stale提示另卡处理，本卡不改前端。
